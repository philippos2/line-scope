# LineScope 開発ロードマップ

仕様の正本は[文書入口](deliverables.md)で選ぶ。本書は完成までの工程を管理し、PR・テスト件数を進捗率へ換算しない。

## 完成の基準

requirements §1とacceptance-criteriaに従い、開発依頼者が操作して業務の流れと仕組みを確認できるデモ・習作を完成させる。商用顧客・SLA・任意の自然言語質問への安定性・一般品質の数値閾値を完成条件にしない。認可・承認・原子性・Evidence・未知の保持は維持し、失敗を成功に変換しない。

## 現在の進捗

**全体の進捗は約90%（実装・代表通し確認済み、最終版の検証と利用者確認が残る）。** 代表API試験の成功をプロダクト全体100%とした以前の報告は撤回する。バックエンドの対象機能と常設の全必須部品は接続済み。Frontendは機能の羅列から、設備選択→調査→比較→根拠→変更準備→承認・実行の6工程へ組み直している。完成はUIから一連の業務を実行できることと、開発依頼者の操作確認まで含めて判断する。

| 利用できる経路 | 到達点 |
|---|---|
| 設備調査・Graph・Evidence | 実PostgreSQL／Neo4jの下流・上流・共通依存・代替構造・SPOF。UIと構造化APIから参照可能。実停止・能力・安全を到達だけで認定しない |
| 文書検索・引用 | 実Embedding／Qdrant、正本照合、版更新、再構築、停止時拒否。一般検索品質の保証とは別 |
| 正式入力・比較 | 経済・能力・安全・対応計画・故障履歴の登録／訂正、共通条件の比較、出典・version・未知の保持 |
| BS-03・Golden代表経路 | #254 merge済み。条件付き150日、能力不足30・条件付き4時間、修理／交換／継続の費用と時間、六次元の判断材料 |
| 承認付き更新 | 明示準備→別承認者→requester確定、競合・再送・履歴・Outbox。代表UI経路も確認済み |

## 工程と残PRの概算

| 工程 | 作業と現在の状態 | 完了条件 | 概算PR |
|---|---|---|---:|
| 1 全必須部品を常設へ導入 | PostgreSQL・Neo4j・Projection・Qdrant・LLM・Embedding・API・Frontendを接続。文書投入、実検索と引用のブラウザ確認は完了 | 設定・起動・文書投入手順を今回のPRへ含める | 工程2と同じPR |
| 2 シナリオに沿うUIと通し確認 | 6工程への改修、比較→Evidenceの引継ぎ、別ユーザー承認と元依頼者実行、実行後の再比較。初回実機通し成功、最終版の確認・CI・引渡しが残る | UIだけで通したreport、画面、手順、最新headのCI成功 | **1（今回）** |
| 3 開発依頼者の操作確認 | 操作の流れ・表示内容を実際に確認してもらい、支障があれば修正する | 一連の業務を操作できると確認する | **0〜1（指摘内容による）** |
| **合計** | 常設構成とUIを同じ業務単位へ集約。確認だけの独立PRは作らない | | **1〜2** |

## 完成後の改善課題

以下は既知の制限であり、現在のデモ完成を阻害する必須工程にしない。

- ローカルLLMの待ち時間と質問による不安定さ。Read全体は既定120秒。Tool提示の絞込み、モデル・context・実行方式の比較は実測して判断する。
- 一般LLM／検索品質。90秒条件のRead baselineは3/5、下流・共通依存はモデル応答検証で失敗。120秒の個別下流診断は応答できたが、モデルがPRECEDESを除くfilterを選んで期待6件に対し2件となりfixture不合格。Graphエンジン自体の不具合や単なるモデル速度問題と混同しない。
- 一般品質の数値閾値、任意質問への全件成功、全UI variant、高負荷・商用SLA・本番災害復旧の保証。
