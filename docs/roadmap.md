# LineScope 開発ロードマップ

仕様の正本は[文書入口](deliverables.md)で選ぶ。現在の改修対象は**シナリオ1：停止したM-204を調べ、M-208を代替候補として提示する流れ**に限定する。

## 現在の到達点と不足

設備・依存関係・正式入力・損害額算定・代替探索・能力評価・承認の基盤はある。しかし、現行UIの入口は算定データ検索に依存し、代替候補と能力を主画面で自動提示する導線も揃っていない。常設データは二台停止の構成であり、今回見せたいシナリオ1の初期条件と異なる。したがって、シナリオ1が完成したとは扱わない。

| 残項目 | 必要な改修 |
|---|---|
| 設備を探す | search_equipmentを非LLM直接経路へ追加。初期画面に設備を固定表示しない |
| 関係と影響 | 一台の選択から下流・上流を取得。損害額データがなくても図を表示 |
| 損害額 | M-204停止・P-100／P-200の登録条件で20万円／時間。登録状態・期間・内訳・未登録理由を表示 |
| 代替提示 | 下流の到達製品と起点除外から候補を自動探索し、M-208を図と主画面へ提示 |
| 能力と未確認条件 | 候補の能力入力を選択しサーバ比較。P-100について必要60・空き80。安全・品質・他製品を確認済みにしない |
| 初期データ | シナリオ1をJSON一ファイルへ。薄いローダーとCLIから新専用環境へ投入し再構築。既存シード・旧環境は保持 |
| 画面・受入 | 左検索、中央図、その下に額と提案、右属性、下段補助機能。S1-01〜08を実画面で確認 |

詳細は[UI設計案](design/frontend-redesign-proposal.md)、[残項目と改修計画](design/scenario1-implementation-plan.md)、[画面案](design/scenario1-wireframes.svg)を参照する。

## 文書PRは完了、残る実装は2件

最初に仕様整理・残項目・実装計画を文書PRで確認する。その承認後に実装PR 1、その報告と別承認後に実装PR 2へ進む。文書PRの作成・mergeだけを実装着手の指示と解釈しない。

| 工程 | 状態 | 内容と完了条件 | 残PR |
|---|---|---|---:|
| 設計・計画 | #264 merge済み | シナリオ1の範囲・配置・データ・ローダー・受入・分割を確認 | **0** |
| PR 1：検索とJSONデータ | 文書mergeと続行指示を受け再開 | 非LLM設備検索、JSON＋loader＋CLI。専用実DB／Graphで候補・20万円・能力60／80とガードを照合 | **1** |
| PR 2：UIと通し確認 | 実装PR 1の報告・mergeと別承認後 | 一画面導線、自動提案、文言・状態制御、実ブラウザS1-01〜08、操作文書・CI・片付け | **1** |
| 利用者確認 | PR 2引渡し後 | 初めて使う人が検索から影響・額・代替へ到達できるか確認 | PRに数えない |
| **合計** | **承認前の実装は禁止** | **今回の実装工程1＋別承認後のUI。検証専用PRは増やさない** | **2** |

不具合修正PRを今から追加予定にしない。実際に必要になれば指摘をまとめて判断する。新たな契約上の不足が判明した場合は影響と工数を先に報告し、黙ってPR数を増やさない。

## 今回の対象外

二台同時トラブル、共有損害、複数起点の比較・分類、検索行の算定バッジ、仮想停止金額の契約、一般的なLLM品質改善、商用SLA、自動異常検知・制御は追加しない。旧案は[UI設計案の後続事項](design/frontend-redesign-proposal.md#8-今回扱わない後続事項の保存)へ保存し、今回の作業対象にしない。

認可・承認・原子性・未知と0の区別は維持する。今回の代表シナリオの成功を全業務受入の合格や全体100%とは扱わない。
