# LineScope 開発ロードマップ

仕様の正本は[文書入口](deliverables.md)で選ぶ。本書は業務シナリオの完成までの工程と残項目を管理する。PR数や試験件数を進捗率へ換算しない。

## 完成させる業務シナリオ

工場で機材トラブルが発生し、調査するとM-204・M-208に異常がある。影響する工程・生産作業・製品と根拠経路を把握し、時間当たり損失と不足情報を確認する。修理・交換・暫定対応等を比較し、人が判断して承認付き変更を行い、再調査する。

- 関係Graphを中心に、異常対象・影響範囲・損失を同じ調査の流れで確認できる。
- 損失は登録根拠と評価条件に基づく推定として示す。実際に確定した損害や工場全体の損失と無条件に同一視しない。
- 未知を0にせず、共通の影響先・共有費用の二重計上を防ぐ。加算不能なら個別値と理由を示す。
- 対応後は保存された変更結果と再取得した状態・影響・損失を確認する。状態変更だけで生産能力・安全・品質の回復を認定しない。

業務上の根拠は[UC-B01〜09・17](requirements/use-cases.md)、[BS-02・09・16・19](implementation-design/business-scenarios.md)、[受入基準](requirements/acceptance-criteria.md)。実設備の自動検知・制御や自動復旧シミュレータは今回の実装対象に含めない。固定デモデータから調査を開始できればよい。

## 現状と不足

既存のGraph中心UI第1〜3段階は#256〜258でmerge済み。ただし、これを上記シナリオの完成とは扱わない。**残り機能実装は基本2 PR、予備を含め2〜3 PR。P0の計画整理は#260でmerge済み。** 利用者確認はPR数に加算せず、その指摘に必要な修正だけを予備として計上する。

| 項目 | 現在あるもの | 残項目 |
|---|---|---|
| 工場・異常データ | M-204に工程・作業・製品・インフラの関係。M-208は主にM-204の代替候補 | P1でM-208自身の関係と2台停止、共有／個別製品、損失・修理／交換・能力・安全の入力、参考文書を追加。常設環境への導入・実検索はP2 |
| 影響分析 | 単一起点の下流・上流、共通依存・代替・SPOF | P1で設備別の影響と共通世代を返す読取APIを追加。P2で同じ調査として画面へ接続 |
| 時間当たり損失 | 修理案のSTOPPAGE項目から登録損失率を計算。正式入力比較の結果に表示 | P1で製品・scope_keyを対応付けた正式入力と複数設備の読取集計を追加。P2で調査画面へ接続 |
| UI | 「対応案を比べる」内で入力選択・比較後に「仮想停止の損失率」を表示 | 調査結果の目立つ位置に被害額の要約と取得導線。金額・単位・対象・期間・根拠・未算出理由を表示し、経済入力の編集でも追加の損失範囲を保持する |
| 対応と再確認 | 正式入力比較、RAG、Prepare→Approval→Execute、再取得 | 新しい工場データで調査→損失→対応→再調査を実UIから通して確認 |

既存の`loss_per_hour`は選択した修理案の停止損失率であり、工場の現在被害額ではない。既存値を単にGraph上へ移すだけでは完了しない。旧「残り実装0 PR」の判断は、この業務上の接続不足を含めて見直す。

## 残工程とPRの粒度

| 工程 | 実施内容 | 完了条件 | 概算PR |
|---|---|---|---:|
| P0 計画整理 | 残項目・UI方針・依存関係・ガント・見積もりを記録 | 未実装を明示し、次の実装対象が特定できる | **0（#260 merge済み）** |
| P1 工場データと影響・損失の接続 | 実装・ローカル検証済み、今回PRで引渡し。2台停止の初期Graphと正式入力、重複を排除する損失集計、読取API、Snapshot v7、参考文書と投入手順を追加。新規20件・既存回帰193件が成功 | 2台の影響と時間当たり損失を実DB・実Graphで再現。共有影響の重複防止、未知、条件不一致、非CURRENTを検証 | **1** |
| P2 UI改善とシナリオ完走 | 異常設備を選ぶ入口、Graphと被害額要約、内訳・根拠、比較・承認・更新後再調査を接続。P1で定義する結果を表示 | 実ブラウザで2台の異常発見から対応後の再確認まで操作できる。被害額が比較フォームの奥に隠れず、金額未取得時も理由と次の操作が分かる | **1** |
| P3 修正予備 | 通し確認・利用者確認で判明した必要な不具合をまとめて修正 | 完成条件に関係する指摘を解消。新たな一般機能の追加は混ぜない | **0〜1** |
| **残り合計** | **P1・P2の実装・確認・必要な修正** | P1・P2のPRそれぞれに検証を含める | **2〜3** |

PRをBackend / Frontendやデータファイル単位で細分化しない。P1はデータと計算を通し、P2は利用者が操作できる体験を通す。実DB・ブラウザ検証を最後に独立した必須PRとして先送りしない。P3は不具合がある場合だけ使用する。

## ダミーデータの整備範囲

- M-204・M-208に名称・役割・状態・異常の背景を揃え、それぞれを使う工程・生産作業と影響製品を登録する。
- 共有する影響先と片方だけの影響先を用意し、2台を調査する意味と重複集計の問題を再現する。
- 時間当たり損失、適用期間、対象範囲、加算条件、出典を正式入力として揃える。金額はデモ仮定として明示し、既存試験fixtureの数値を自動的に業務値にしない。
- 修理・交換等の費用と停止時間、能力・安全条件、計画・履歴と参考文書を同じシナリオに合わせる。2台とも異常のときM-208を無条件に利用可能な代替にしない。
- 新設備は、代替の説明に必要と判明した場合だけ加える。設備数を増やすこと自体を完成条件にしない。
- 再現用データの投入・再開手順を用意し、既存の常設データを黙って上書きしない。開始前後の状態と、利用者が加えた変更の保持を確認する。

### P1で確定・照合する設計事項

複数設備間の損失を加算できるかは現行の単一修理案内の`independent`指定だけで推定しない。影響先・費用範囲の識別、重複の排除、根拠の適用条件を正本文書へ反映する。同一製品・同一範囲は1回だけ計上し、独立性が明示された異なる範囲だけ加算する案をPOが承認済み。不一致・未登録・期間不一致は完全合計を出さない条件を正本へ反映した。

損失の評価期間・異常対象の選び方、累積損失を算出する場合の開始終了と復旧後の扱いも同様に明示する。壁時計の経過だけで自動的に被害額を増やさない。

## 今回の完成条件に含めない改善

- ローカルLLMの一般的な速度・任意質問の品質改善。Read上限は既定120秒。今回の明示操作による調査をLLMの自由な選択に依存させない。
- 商用SLA、高負荷、全UI variant、全端末、本番災害復旧の保証。
- 実設備からの自動異常検知、実設備の自動復旧・制御。

認可・承認・原子性・Evidence・未知の保持は既存どおり完成条件から外さない。
