# LineScope 要件定義書

## 1. 目的

LineScopeは、工場の設備・工程・製品・保全情報・依存関係を統合し、設備異常・故障・計画停止時の運用上の意思決定をEvidence付きで支援するシステムである。影響範囲、能力、リスク、経済的損失、対応策の費用・時間・残存リスク、不足情報を関連付けて提示する。最終意思決定はエンドユーザー、Approvalは承認者、Executeは元requesterが行う。自然言語による参照・分析・変更準備はそのための手段とする。

業務データ更新は、明示的な更新要求、対象特定、権限確認、変更前後提示、認証済み承認、実行時再検証を経て行う。

本プロダクトは開発依頼者が業務システムの構成と操作を確認するためのデモ・習作とする。商用顧客向けの実運用サービスやSLAを完成基準にしない。正式入力・実ミドルウェア・代表業務シナリオ・承認付き更新が一連の操作として形になっていることを優先する。待ち時間、任意の自然言語質問への安定性、一般検索品質の改善は後続課題とし、既知の制限を明示する。Safety / Security、認可、原子性、不明の保持、未実施を成功としない原則は維持する。

## 2. 本書の範囲

本書はWHATを定義する。DB製品、GraphDB製品、VectorDB製品、実装言語、Framework、具体API形状は規定しない。

### 2.1 要件・受入・設計の順序

最上位は§1の業務目的、ユースケースはその達成を定義する要件、Business Scenarioはユースケースの受入仕様である。Ontology・データモデル・DB・API設計はそれらを実現する下位設計、Outbox・Projection・lock等はさらに下位の実現方式とする。

下位仕様と上位意図が矛盾したら、Safety / SecurityのHard Constraintを除き、上位を優先して下位を再設計する。既存DBやToolでできないことを理由に上位ユースケースを対象外へ移さない。未定義の業務ルールはPO判断として明示し、実現方式の都合で補完しない。各事項の正本文書はdeliverablesの責務表に従う。


## 3. 基本機能要件

### R-01 自然言語要求受付
利用者の自然言語要求を受け付ける。

### R-02 業務情報取得
設備、保全、生産運用、依存関係、更新履歴等の業務情報を取得する。

### R-03 複数情報統合
複数の業務情報を組み合わせて回答・分析する。

### R-04 業務データ更新
明示的な更新要求がある場合、権限・承認・業務制約を満たしたうえで更新できる。

### R-05 更新結果確認
更新対象、成功・失敗、変更前、変更後を確認できる。

### R-06 複数ターン確認
対象が曖昧な場合等、利用者との追加確認を経て処理を継続できる。

## 4. 依存関係・Graph業務要件

### R-07 依存関係取得
設備、工程、生産作業、製品、インフラ等の関係を取得できる。

### R-08 多段探索
一段に限定せず複数段探索できる。

### R-09 下流影響伝播
停止・故障・保全等による直接・間接の下流影響を特定できる。

### R-10 上流依存探索
対象成立に必要な上流要素を探索できる。

### R-11 共通依存探索
複数対象に共通する上流依存要素を候補として特定できる。

### R-12 代替経路探索
通常経路を利用できない場合、定義済み関係から代替経路候補を探索できる。

### R-13 単一障害点候補
重要対象への成立経路について、代替がない要素を候補として提示できる。

### R-14 依存関係更新
権限と承認を満たした利用者は、依存関係を登録・変更・無効化できる。

### R-15 経路根拠
分析結果の根拠となる代表経路を確認できる。

### R-16 不完全探索の明示
探索上限到達時、完全探索済みと誤認させない。

## 5. Agent要件

### R-17 処理選択
要求に応じて参照、Graph分析、更新準備等を選択する。

### R-18 必要情報取得
必要情報を取得してから回答・分析・更新準備を行う。

### R-19 捏造禁止
存在しない業務データ、経路、承認、更新結果を事実として生成しない。

### R-20 任意対象選択禁止
更新候補が複数ある場合、Agentが任意に一つを選んで更新しない。

### R-21 自律更新禁止
明示的な更新要求なしに業務データを更新しない。

### R-22 候補と事実の区別
原因候補、共通依存候補、代替候補、単一障害点候補と確定事実を区別する。

## 6. 更新・承認要件

### R-23 対象一意性
更新対象を一意に特定する。

### R-24 必須情報
不足値を推測補完しない。

### R-25 変更前後提示
更新前に対象、操作、変更前、変更後予定を提示する。

### R-26 認証済み承認
確定更新前に、認証済み承認者の明示的承認を必要とする。

### R-27 承認経路
自然言語の解釈だけを承認成立条件としない。

### R-28 承認内容一致
実更新内容は承認済みSnapshotと一致しなければならない。

### R-29 承認失効
対象、操作、Snapshot、version等が変化した場合、承認を失効させる。

### R-30 承認期限
承認は承認成立から30分で失効する。

### R-31 実行主体
承認済み更新は、認証済みの元要求者による明示的な実行要求でのみ開始する。

### R-32 原子性
一つの更新要求に含まれる複数変更は部分確定を正常完了として残さない。

### R-33 重複更新防止
同じ更新要求または承認を二重実行しない。

### R-34 CREATE競合
CREATEはversionではなく一意性、業務キー、冪等性に基づいて競合を検出する。

### R-35 更新履歴
更新要求、承認、対象、変更前後、結果を追跡可能とする。

## 7. 一貫性要件

### R-36 正本最新性
確定済み更新後の正本参照は最新確定状態を返す。

### R-37 派生Graph最新性
正本との同期が確認できる場合のみGraph分析を正常な最新結果として返す。

### R-38 非同期反映中
派生Graphが追随中または異常状態のとき、古い結果を正常な最新結果として返さない。

### R-39 並行更新
並行更新によって禁止循環、重複、二重承認消費等の不整合を成立させない。

### R-40 設備割当一意正本
ProductionOperationとEquipmentの割当情報は単一の正本から管理し、GraphのUSES関係はその正本から派生させる。

## 8. 例外分類

- 対象不存在
- 対象非一意
- 必須情報不足
- 権限不足
- 承認未取得
- 承認不一致
- 承認期限切れ
- 承認失効
- 承認二重消費
- 業務ルール違反
- version競合
- CREATE競合
- 重複要求
- 更新失敗
- Graph非最新
- Graph利用不可
- Graph再構築中
- 探索上限到達
- 代替経路不存在

## 9. プロダクトがやること（対象業務）

単一工場の業務判断支援を対象とする。以下はプロダクト全体の目標であり、現在の実装済み一覧ではない。

| 対象 | 実現する業務目的 | 要件・ユースケース |
|---|---|---|
| 業務Objectの把握 | Equipment、Process、ProductionOperation、Product、InfrastructureResource、設備状態・保全予定・実績・履歴を関連付けて確認する | R-01〜03、UC-01〜03、UC-B12・16 |
| 依存・影響分析 | 直接／間接影響、影響経路、上流依存、共通依存、代替、SPOF候補を根拠付きで提示する | R-07〜16、UC-04・16〜20、UC-B01 |
| 生産と経済の評価 | 能力低下、代替の吸収可否、必要量不足、停止・劣化損失、納期・復旧期限を定義済み入力・ルールで評価する | R-B02・04・07、UC-B02・03・05・11 |
| リスクと対応案比較 | Safety / Production / Quality / Delivery / Cascade / Economic riskを区別し、修理・交換・継続・代替を共通条件で比較する。Hard Safety Constraint違反案を除外する | R-B03・05・06・08、UC-B04・06〜10・12 |
| Evidenceと不足情報 | 正本・経路・文書・計算入力と式・仮定を追跡し、未知と不完全性、推定と確定を区別する | R-19・22、R-B09・10、UC-B13・15 |
| 承認・実行と結果確認 | 明示要求からPrepare、認証済み承認者のApproval、元requesterのExecuteへ進み、結果・履歴・現在値を確認する | R-04〜06・23〜40、UC-05〜15・21、UC-B14・17 |
| 分析ワークスペース | Object・Graph・Evidence・比較案・Actionを関連付けて確認できるFrontendを提供する | §13。[画面設計](../design/frontend-console.md) |

中心はUC-B09とGolden ScenarioのDecision Packageである。検索・チャットは業務判断の入口であり、Graph表示やOntologyの構築そのものを最終目的としない。対象内の能力・経済・安全等に未確定の入力があれば§14.3で判断し、計算できない範囲と既知の結果を明示する。

### 9.1 今回のデモでやること

§9はプロダクト全体の業務目標。本節と§11.2は今回完成させた技術検証デモの範囲であり、すべての目標を実証済みとする一覧ではない。既存の「やること／やらないこと」の退避案から有効な定義を取り込み、PR #277・#278の確定範囲を反映する。検証方法・観測・限界は[本デモアプリで検証したこと](../demo/verified-findings.md)、投入データは[シナリオ1](../demo/scenario1.md)を参照する。

| やること | 範囲と限定 |
|---|---|
| 型と関係で単一工場を表す | 架空の設備・工程・生産作業・製品・インフラと、依存・供給・作業順序・設備使用・代替等をdomain-modelの意味で扱う |
| 設備を検索する | 名称・コードの共通正規化を左ペインと質問欄で使う。一意でない対象は先頭を選ばず確認する。未登録の別名は推測しない |
| 登録関係を調べる | 上流依存・下流到達・共通依存・一段代替・SPOF候補を、関係の方向・探索完全性・Graph世代・根拠とともに示す |
| 共通必須電源を評価する | R-02をM-204/M-208の必須電源とし、登録供給状態AVAILABLE／UNAVAILABLE／UNKNOWNを読取専用で保持・取得・評価する。登録時刻とDB読取時刻を分ける |
| 登録条件による損害額・能力を示す | 初期データのM-204停止損害はP-100/P-200の計200,000円／時間。M-208のP-100必要能力60・空き能力80を条件付きで評価する。P-200はその能力入力では未評価 |
| 正式入力で対応案を比較する | 経済・能力・安全・対応計画／履歴の選択、共通期間、出典・版、既知小計・総額不明・評価対象外を区別する。未知を0にせず、UIで計算しない |
| 質問欄で限定照会する | [固定9観点](../design/demo-question-chat.md)へ全文一致した場合だけ型付きReadとEvidenceから定型回答する。質問用UIはテキストボックスと送信操作。確認・案内も同じ会話で行い、LLM分類・生成を使わない |
| 出典・文書を参照する | 質問欄とは独立した文書検索・正本照合と、取得済みGraph／根拠の参照を提供する。Embedding検索と限定質問を同じ機能とは扱わない |
| 4カテゴリの入力を登録・訂正する | 経済・能力・安全・対応計画／故障履歴の候補と自由入力を扱い、明示準備→保存内容確認→権限規則に従う承認→元requester実行を分離する。準備完了だけでは値は変わらない |
| 整合性を保って結果を確認する | 認証・認可・version・Snapshot・再送制御・監査・Outbox・再取得を用いる。実行結果不明と失敗、確定結果と現在値を区別する |

入力候補は登録データから取得し、0件・取得失敗・続きありを区別する。初期データに安全入力・対応計画／故障履歴がない場合、候補は生成しない。未登録は候補機能の未実装を意味しない。変更要求IDは人が受け渡し、ID入力または接続中に作成した直近の要求から開く。承認待ち一覧・通知・IDサジェスチョンは追加しない。

## 11. プロダクトがやらないこと（スコープ外）

| スコープ外 | 境界 |
|---|---|
| AIによる自律的な最終意思決定・Approval / Execute | AIは調査・比較・変更準備を支援する。案の提示を承認や確定実行と扱わない |
| 実設備の自動制御 | 設備状態や計画等の業務情報を承認付きで変更する。PLC等への指令・設備停止を直接行う製品ではない |
| 在庫・受注・BOMの完全管理 | 必要な生産量・buffer等は判断支援の入力として扱えるが、取引・在庫・受注全体を管理するERPを構築しない |
| 本番MES / ERP接続 | 現スコープでは実業務システムとの本番連携を実装しない。判断用入力の保有と外部システム連携を区別する |
| 複数工場・マルチテナント | 単一工場を対象とし、工場間・tenant間の管理は含めない |

不足データから根拠のない事実・安全保証・将来故障確率・総合Risk Scoreを生成しない。これは機能範囲を削る理由ではなく、対象内の全分析に適用する品質・Safety / Security上の制約である。

### 11.1 対象外と混同しないもの

| 区分 | 扱い |
|---|---|
| 後続フェーズ | 今回のデモに追加しない機能と、恒久的な対象外を§11.2で区別する。未採用候補を実施予定とは扱わない |
| PO判断待ち | 能力・費用・安全・計画・履歴・新情報権限等の意味はPO-B01〜08で確定する。対象内だが推測で実装しない |
| 実装・検証の区別 | Graph、文書検索、Approval / Execute等を一律に未実装としない。確認方法と未検証は[検証結果](../demo/verified-findings.md)、進捗は[ロードマップ](../roadmap.md)で示す |
| 下位設計の限界 | 過去as_ofの限定、一段代替、既存Snapshot形状、将来停止予約の未定義等はdomain / API / transactionの現行契約。上位要件との不整合は§2.1に従って明示再設計する |

スコープ変更は業務目的・ユースケース・受入仕様への影響を明示して判断する。既存制御を黙って解除せず、Safety / Securityを維持し、必要な下位契約・テストを改訂する。

### 11.2 今回のデモでやらないこと・結果から主張しないこと

§11の恒久的な対象外に加え、以下の境界を維持する。対象内の未検証を「対象外」として消したり、実装しただけで検証済みにしたりしない。任意の将来候補は採用・実施予定を意味しない。

| 分類 | やらないこと・主張しないこと |
|---|---|
| 実運用の保証 | 登録状態を実際の稼働・通電確認としない。到達候補を実停止とせず、構造成立・登録供給AVAILABLE・能力充足を運転許可や安全・品質の認定にしない |
| 経済性・予測の保証 | 登録条件の損害見積もりを実損害や工場全体の損失としない。代替案の費用総額は現実装で算定しないため、データ追加だけで算定できるとは説明しない。稼働中設備の仮定停止損害や将来故障確率を新たに推定しない |
| 未登録データの補完 | 安全入力・対応計画／履歴を候補表示のために捏造しない。0件を未実施・不存在の証明とせず、取得失敗を未登録にしない |
| 汎用自然言語理解 | 任意の口語・複合質問・設備間比較を理解するとは主張しない。メーカー・保証・倉庫・来社予定等を近い観点へ置換せず、対応外の案内を返す。質問専用の観点選択・LLM候補UIは設けない |
| 今回追加しない機能 | 承認付き供給状態変更、別名・略称の登録基盤、未対応語彙を育てるログ／編集基盤、承認待ち一覧・通知、検索行の追加バッジ、シナリオの拡充は実装を約束しない |
| 情報の完全性 | 一段代替を連鎖置換や完全代替とせず、現在登録情報の過去時刻評価を完全な時点復元としない。工場内の関係や在庫を網羅したとはしない |
| 検証の一般化 | 固定データの試験成功を実工場での有用性、Graph DBだけの方式に対する優位性、商用SLA、一般的な応答品質の証明としない |
| 未検証 | 他3カテゴリの実書込み通し、UNAVAILABLE／UNKNOWNの実ブラウザ、元の中断原因、正式環境起動直後のpartial原因などは[未確認事項](../demo/verified-findings.md#未検証事項と追加検証の条件)として保持する |

## 12. v1業務入力・状態値

| 対象 | 許可値・必須項目 |
|---|---|
| EquipmentState UPDATE | state_code: RUNNING / STOPPED / UNDER_MAINTENANCE / UNKNOWN |
| MaintenancePlan CREATE | plan_code、equipment_id、planned_start、planned_end、plan_status必須。plan_status: PLANNED / CANCELLED |
| MaintenancePlan UPDATE | planned_start、planned_end、plan_statusの明示patch。合成後も必須項目を満たす。plan_code・equipment_idは変更不可 |
| MaintenanceRecord CREATE | record_code、equipment_id、performed_at、空でないresult必須。maintenance_plan_idのみ任意NULL |
| ProductionOperation UPDATE | planned_status: PLANNED / CANCELLED、planned_start、planned_endのpatch、または明示期間付きEquipment集合置換。合成後の予定状態・開始・終了は必須 |
| DependencyRelation | endpoint型・ID、relation_type、effective_from、明示effective_to（NULL可）、required必須。型・循環はdomain-modelに従う |

planned_start < planned_end、effective_from < 非NULL effective_toを要求する。必須業務値をNULLにしない。patchは少なくとも1つの実変更を含む。設備状態は許可集合内の変更を許可し、保全・生産予定はPLANNEDとCANCELLED間の変更を許可する。追加の状態遷移制限は設けない。予定状態に実績状態を追加しない。

保全実績登録は設備状態・保全予定・生産予定を自動変更しない。maintenance_plan_id指定時は同じequipment_idの既存計画であることを要求する。DependencyRelationのrequired未使用種別はfalseを要求し、true入力を拒否する。関係自体の必須性はdomain-modelの規則で評価する。

EquipmentState更新の現在状態・履歴は同一Transactionで保存し、現在状態の更新時刻と履歴effective_at / recorded_atは確定実行のサーバ時刻を記録する。既存のEquipmentState UPDATEは過去・未来の状態登録を行わない。UC-B14の将来停止は保全予定として登録し、このUPDATEへ予約実行の意味を付与しない。UUID・監査時刻・version等の技術メタデータ生成と業務値の推測を区別する。

### 単純費用回収の登録条件

PO-B01の単純費用回収期間は、共通期間の経済入力に日次稼働・一定稼働・交換で劣化損失が解消する仮定と出典を明示した場合に計算する。交換案の独立加算可能な直接費を、継続案の独立加算可能な毎稼働時間の劣化損失率×日次稼働時間で割る。比較期間の率を一定と置く条件付き単純試算であり、両案の損益分岐・期間外の実損失予測・交換の推奨ではない。劣化損失が全稼働時間に適用される条件を満たさなければ算出しない。

日次稼働は0〜24時間の十進文字列または不明。一定稼働をtrueとする場合は、比較期間の明示稼働時間と整合しなければならない。仮定のfalse／不明、費用範囲の未確認、非独立・未知の損失、稼働0時間では日数不明。劣化損失率0は回収日数なしと区別する。端数は日数を過小表示しないよう小数6桁で切り上げる。既存の承認・確定・閲覧権限を適用する。

### 複数設備の影響と時間当たり損失

UC-B05の停止損失推定では、明示選択した設備の現在状態、実Graphの影響候補製品、正式経済入力の損失範囲を照合する。同じ製品・同じ損失範囲は複数設備から到達しても1回だけ計上する。異なる範囲は独立加算可能と明示された場合のみ合算する。範囲・率・出典等の不一致、未登録、期間不一致、探索不完全では完全合計を出さず、判明小計と理由を示す。

数値は登録条件に基づく円／時間の推定であり、実損害確定値や工場全体の損失ではない。実停止・復旧・能力・安全をGraph到達や状態更新だけで認定しない。累積損失は今回算出せず、壁時計から増加させない。
