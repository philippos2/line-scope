# 本デモアプリで検証したこと

LineScopeは、単一工場の架空データを使ったライトウェイトオントロジーの技術検証デモである。本書は、何を試し、観測から何が言え、何までは言えないかを整理する。機能の実装一覧や実運用の品質保証ではない。

範囲の正本は[要件定義のやること](../requirements/requirements.md#91-今回のデモでやること)と[やらないこと・主張しないこと](../requirements/requirements.md#112-今回のデモでやらないこと結果から主張しないこと)。本書から新しい仕様・受入条件を追加しない。

## 対象版と根拠の読み方

現在のデモはPR [#277](https://github.com/philippos2/line-scope/pull/277)の質問欄、[#278](https://github.com/philippos2/line-scope/pull/278)の共通電源・登録供給状態、[#279](https://github.com/philippos2/line-scope/pull/279)の正式環境への移行を反映する。正式環境の製品ソースは#278 mergeの`55965a327366be4300b40d3e3ed8f595d9e6c91a`に固定されている。接続・運用は[正式環境文書](environments.md)を参照する。

| 根拠の種類 | 本書で意味すること | それだけでは言えないこと |
|---|---|---|
| 実装済み | 設計・実装記録にその機能がある | 正常・障害を含む動作の確認完了 |
| 設計／静的確認 | 正本文書の責務・意味・境界を確認した | 実行時にも常に成立すること |
| 自動試験 | 制御した入力・障害や実DB等で、記録されたassertionが成功した | 同じ障害を実利用環境で観測したこと |
| 直接API | 起動した実APIへ要求を送り、応答とEvidenceを照合した | 全UIでの表示・操作や全入力の成功 |
| ブラウザ | 指定環境・条件で表示と操作を確認した | 未操作の状態や他条件の網羅 |
| 未検証 | 対応する実行根拠がない、または取得できていない | 実装済みや別の成功による代用 |

本書の整理時には製品試験・モデル・API・ブラウザを再実行していない。以下は既存の原記録を照合した結果で、記録当時の版・データ・環境の限定を保持する。過去の履歴にある5174等は当時の接続先であり、現在の起動先ではない。

## A. ライトウェイトオントロジーの有用性

| 項目 | 内容 |
|---|---|
| 目的・仮説 | 設備・工程・生産作業・製品・インフラを型と意味のある関係で表すと、設備単体の属性参照では分からない依存先・到達先・代替構造を調べられるか。 |
| 方法 | **設計確認**：関係のendpoint型・方向・必須性と一段代替を確認。**自動試験**：固定Graphによる到達・AND充足・除外・代替・SPOFの業務シナリオ。**直接API／ブラウザ**：M-204の下流と、M-204/M-208のR-02上流依存を確認した記録を照合。 |
| 観測結果 | M-204から下流6対象（工程・生産作業・製品）を到達候補として取得した。F2では両設備から共通電源R-02を表示した。DEPENDS_ONの保存方向と停止影響をたどる方向を分け、CAN_SUBSTITUTEを通常の到達edgeと混同せず評価した。 |
| 結論 | この固定モデルでは、型・関係意味論と探索・充足規則を組み合わせ、異なる業務概念をまたぐ根拠付きの構造分析を実行できた。単にedgeがあることと、必須条件が成立することを分けられた。 |
| 限界 | 実工場の関係が網羅されることや、到達先が実際に停止することは未実証。Graph DBだけを使う方式との比較・アブレーション実験はなく、オントロジー導入の定量的優位・ROIは主張しない。OWL/RDFの汎用推論を検証したものでもない。 |

## B. データモデルと評価規則の分離

| 項目 | 内容 |
|---|---|
| 目的・仮説 | 概念・登録データ・登録状態・評価規則・Evidence・表示を分離すると、同じ構造について状態による判定差と、その根拠を説明できるか。 |
| 方法 | **設計／静的確認**：domain-model、data-model、architecture、API契約の責務を照合。**自動試験と直接API**：F2でGraph構造を保持したまま異なる初期供給状態を評価し、正本参照・version・時刻を確認。 |
| 観測結果 | PostgreSQLを業務正本、Neo4jを派生Graphとして扱い、設備・供給状態は正本から読む。F2の9応答では構造成立を維持したまま利用可能性が変わり、Evidenceには供給状態レコードとversion、登録時刻とは別のDB読取時刻が残った。 |
| 結論 | この経路では構造そのものと状態評価を分離し、評価に使った登録情報を追跡できた。表示は取得結果・規則の結果を使い、UIやLLMが業務値を補完する責務にはしなかった。 |
| 限界 | 各ストア・状態の観測は分散Transactionによる同時Snapshotではない。分離した設計だけで全実行の正しさを証明せず、記録された試験とAPI条件の範囲で結論を述べる。 |
| 根拠 | [責務の接続](../design/architecture.md#13-概念から表示までの責務と配置)、[物理データモデル](../design/data-model.md)、[API・Evidence契約](../implementation-design/api-tools.md)、[F2の9応答照合](../history/2026-10-26-alternative-power-investigation.md)。 |

## C. 構造上の代替候補と三値の利用可能性

| 項目 | 内容 |
|---|---|
| 目的・仮説 | M-208がRUNNINGでも、共通必須電源R-02の登録供給状態が不可・不明なら、利用可能な代替設備と断定せず、構造上の候補は保持できるか。 |
| 方法 | **自動試験**：F2追加22ケース（Backend20・Frontend2）と既存回帰の記録。**直接API**：三値ごとに独立した初期DBで初回seed・Rebuildし、重要対象P-100/P-200、除外M-204、候補M-208の同じ構造化要求を各3回送信。**ブラウザ**：AVAILABLEで両設備の上流Graph、供給状態、Evidence、代替提案を操作。 |
| 観測結果 | 下表の各条件で3回とも期待一致。全条件でM-208はRUNNINGかつ構造ESTABLISHED。供給不可・不明でも構造候補は消えなかった。各状態内でレコードversion1・登録時刻・sourceが保持され、DB読取時刻を区別した。AVAILABLEの画面で共通電源と読取専用表示、P-100能力充足と運転許可ではない限定を確認した。 |
| 結論 | 登録された共通依存状態が、構造候補を保持したまま三値の利用可能性へ反映されることを確認した。 |
| 限界 | AVAILABLEでも実通電・実運転・安全を保証しない。UNKNOWNはUNAVAILABLEとは異なる。UNAVAILABLE／UNKNOWNの**実ブラウザ**は未確認で、直接APIと制御値による表示試験を代用の実ブラウザ確認とは呼ばない。P-100の能力評価をP-200へ一般化しない。 |
| 根拠 | [F2の実測・CI・API・画面記録](../history/2026-10-26-alternative-power-investigation.md)、[B案の承認範囲](../design/alternative-power-dependency-plan.md)、[PR #278](https://github.com/philippos2/line-scope/pull/278)。 |

| R-02の初期登録供給状態 | M-208の構造 | 登録条件による利用可能性 | 直接API |
|---|---|---|---|
| AVAILABLE | ESTABLISHED | AVAILABLE | 3/3期待一致 |
| UNAVAILABLE | ESTABLISHED | UNAVAILABLE | 3/3期待一致 |
| UNKNOWN | ESTABLISHED | UNKNOWN | 3/3期待一致 |

状態保存は読取専用。seedは初期投入専用であり、公開済みGraphへ追加・既存状態を上書きする更新経路ではない。承認付き供給状態変更は今回実装しなかった。

## D. 不完全・不明な情報と、適切な保留・拒否

| 項目 | 内容 |
|---|---|
| 目的・仮説 | 取得できなかった情報、正常な0件、状態不明、探索不完全を区別し、別の意味の事実や「存在しない」という断定を返さずに案内できるか。 |
| 方法 | **自動試験**：探索上限、Evidence不足／不一致、認可・取得障害、代替の不完全探索・名称取得失敗等を制御。**直接API**：PR #277の固定46原文各3回で、未登録保全、対応外、対象省略等の応答・公開tool_results・Evidenceを照合。 |

## 未検証事項と追加検証の条件

| 残る事項 | 現在の扱い／追加確認が必要になる条件 |
|---|---|
| 実工場への適用・停止影響・安全・品質・経済効果 | 技術デモから保証しない。実データの網羅性、観測方法、業務受入を別途定める必要がある |
| Graphだけの方式との優位・性能・費用対効果 | 比較実験なし。比較対象・指標を決めた追加検証が必要 |
| 起動直後partialの原因 | 最初の本文未保存。再現時の応答・同期状態・探索制限等の証拠が必要。今回製品修正は行わない |
| 元の通信中断原因 | 当時のNetwork記録なし。既知の応答喪失経路への復帰確認とは別 |
| 経済入力以外の3カテゴリの実書込み | 自動／制御確認と区別。必要時に専用環境・操作・権限を示して明示承認を得る |
| UNAVAILABLE／UNKNOWNの実ブラウザ | API三値確認と表示自動試験はあるが実ブラウザ未確認。画面の追加確認が必要な場合に実施 |
| 一般の口語・別名・複合質問 | 現行9観点の対応範囲外。再導入・語彙拡張は必要性と受入条件を別途判断し、予定として確定しない |
| 正式移行後の新規Embedding検索 | 移行時はmetadata・本文・Index保持のみ確認。検索動作が必要なら設定・モデル・版を固定して別途確認 |

これらは未確認・任意の判断事項であり、承認済みの残実装PRを新たに追加する一覧ではない。[現在の工程](../roadmap.md)と、仕様の[非保証範囲](../requirements/requirements.md#112-今回のデモでやらないこと結果から主張しないこと)を合わせて読む。
