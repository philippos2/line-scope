## 設計と変更

- 4つのEditorとActionPanelへ`OperationFeedback`を接続した。明示的な拒否、応答を確認できない書込、書込成功後の保存状態GET失敗を別に表示する。未分類の書込エラーは安全側に結果不明とし、未作成・未実行を断定しない。エラーコード・診断用リクエストIDは技術情報へ置き、変更要求IDと区別する。
- 専用hookは各操作の中断・存続を管理する。存続中の画面で親signalが中断したときはbusyを解除して結果不明等へ移り、中断前の遅い応答は反映しない。アンマウント・認証解除時も中断して旧画面へ結果を戻さない。APIアクセスと成功応答の解釈は各操作側に維持する。
- 4入力の応答不明後の明示再送は、送信時と同じ入力・保持した同じキーだけを使う。入力が変われば再送不可の理由を表示する。自然文Prepareも同じ指示とキーで明示再送する。新しい指示を不明な操作の再送として受け付けない。
- 既知の要求IDは保存状態確認のGETへ渡す。ID不明なら過去の直近要求を今回の結果とは表示しない。入力・キーは画面メモリ内だけに保持し、接続／対象変更・画面を閉じた後の永続復旧を約束しない。中断済みの親signalを持つEditorから再送しない。
- ActionPanelはPrepare・承認・拒否・実行の成功応答を受けたことを、後続GETと分離して記録する。GETだけ失敗したら完了済み操作の再実行を促さず、同じIDで再取得する。実行応答を失敗表示によって消さず、同じ要求IDのGET再試行でも保持し、既存の更新前通知・元requester実行・本人承認禁止等の条件は維持する。
- Panelの検索エラー・能力の製品検索、W3・R1・R2、工程ガイド・案内コピー・実行後再取得リンク等は今回の修正に含めない。全UIの失敗表示を統一済みとは扱わない。

## PR #272レビューの精査と補強

- backend-transaction-reviewの手順で、当初の12コードを発生箇所・commit／rollback・失敗監査まで静的に照合した。Claudeの「明示拒否は副作用がない」という前提は補正が必要だった。VERSION_CONFLICTの承認失効、APPROVAL_EXPIRED／APPROVAL_INVALIDATEDの別transactionによる失効、失敗監査が保存される場合があり、DB不変とは説明できない。DUPLICATE_REQUESTでは元の保存要求が保持され、以前の成功も否定できない。
- failedを今回の試行の拒否理由の表示と定義し、未保存・未実行や副作用なしの断定とは区別した。成功応答後のGET失敗は明示拒否コードより優先して別表示にする。根拠をFrontend設計へ12行の表で追記した。
- SNAPSHOT_MISMATCHとRESOURCE_NOT_FOUNDは現行Backendに発生箇所がなく、拒否分類の根拠が不足していたため一覧から除外し、未知の書込エラーとして結果不明へ分類した。変数も`knownRejections`として、単なる文言追加が拒否分類の拡張にならないよう責務を明記した。Backend・契約は変更しない。
- ID不明時の長い案内を3項目の箇条書きへ分けた。保持範囲・直近要求との区別・明示再送の条件は維持する。
- 単体のローカルDocker実行（前回61件）と、CIのnpm run check（lint・型・整形・build）は別の確認だとPR本文へ明記する。CIでvitestを実行したとは説明しない。
