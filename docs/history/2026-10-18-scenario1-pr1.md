## 変更

- search_equipmentを「関係分析」の厳密JSON直接経路へ追加。既存dispatcherの引数・Read認可を維持し、LLM生成を使わず検索できる。
- docs/demo/data/scenario1.jsonへ設備・関係・経済入力・能力入力を配置。値はファイルから読み、旧Pythonシードの既定値・動作は変更していない。
- demo_file_seedの固定形式検証・コード参照変換、seed-demo-file --fileを追加。1 MB上限、未知field／重複キー／参照／型を検証し、正式入力は既存make_recordへ渡す。
- 既存lockとseed_graph_rowsを一transactionで利用する。途中失敗は全体rollback。既存状態・版・入力は保持し、再構築中と公開済みGraphへの追加は拒否する。
- テストimageだけへJSONをCOPYするためDockerfileと.dockerignoreを変更。runtimeは指定ファイルのmountを使う。

## 実API照合

新しい専用project linescope-scenario1をJSONから初期化し、Neo4jのschema導入・再構築・Projectionを実行した。APIはlocalhost:8002。専用の私有設定.env.scenario1-demoはmode 0600、Git対象外。旧Frontend localhost:5173を切り替えていない。

専用環境のLLM接続先をhttp://127.0.0.1:9にして、共有LLMを停止せず非LLM経路を実HTTPで確認した。モデル設定はReadAgentを組み立てるために残している。LLM生成の品質試験を行ったという意味ではない。

| 項目 | 実測 |
|---|---|
| 設備名検索 | 第1でM-204を返却。20ms（単一実行、性能保証ではない） |
| M-204の損害額 | 200000円／時間。P-100とP-200を返却。58ms |
| 代替探索 | M-208をcandidatesに返却。代表経路とcurrent_statesにRUNNING。84ms |
| 候補の構造 | 候補structure.determination=ESTABLISHED、availability=UNKNOWN |
| 能力 | 必要60、空き80、capacity_status=SUFFICIENT。比較164ms |
| 比較の条件 | structure=UNKNOWN、safety=UNKNOWN、quality=UNKNOWN、operational_permission=false。残余リスクもUNKNOWN |
| P-200の説明元 | 下流到達製品とselected_inputs.capacity[].input.product_idの差。サーバの製品別未評価一覧ではない |

P-100の構造候補と能力充足があっても、比較の構造利用可能性まで成立したとは扱わない。利用可能性不明を解消するデータは追加しなかった。P-200は「今回選択した能力入力では評価していません」という選択範囲の説明に限る。候補が返らない／追加契約が必要という停止条件には該当しなかった。

## 検証と既存環境の保持

追加は事前見積もりどおり18件：JSON検証8、直接検索4、実DBの保持・原子性・ガード5、実Graph/API1。Docker内で18件成功（最終image、約5秒）。既存シード3種・ReadAgent・正式比較の回帰は69件成功、11.92秒。lint・formatは成功し、既存test・assertionを削除していない。

初回試験ではfloorの通常設備Readを拒否するという試験側の誤認と、初期fatal_errorをNULLとする誤認があった。access-controlの設備Read権限と初期NOT_INITIALIZEDを確認し、それぞれ無効tokenの拒否、実行前後の値保持という検証へ訂正した。失敗を成功扱いしていない。専用環境構築時のDB role password形式不一致も、既存の64桁hex規則に合わせて修正し、正常に再構築した。

既知の警告はStarletteのhttpx非推奨、Neo4jのNULL属性effective_to未存在通知、試験終了時の既存logger出力失敗通知。試験の失敗・skipには変換していない。最新headの全required CIと実測はPR本文へ記録する。
