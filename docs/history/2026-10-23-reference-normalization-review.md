# 表記照合と重複回答の調査・修正

## 目的と現在地

開発者の例は、特定の設備名・質問文を通す条件ではない。名称・コードの表記差、別IDの衝突、取得不完全を共通に扱う。2026-10-23、重複回答の修正後、開発者からClaudeの層分離方針による修正と、許容範囲の判断の委任を受けた。共通検索を実装し、検証中。H6全体の受入合格とはしない。

## 確認した原因

- `equipment_reference.py` は `第` に続く数を半角・全角・漢数字に展開する。`reference_key` はNFKCを使うがcasefoldはしない。共通関数という配置だけでは、名称・コード全般の表記照合を実現したことにならない。
- `scoped_reads.py` は元の表現をコードで一度検索し、表記候補は名称条件だけで検索する。したがって名称の候補展開はコードの大小文字差を解決しない。
- `read_agent.py` にも補助検索の実装がある。片方だけ直すと経路間で差が残るため、置換対象に含める。
- 通常Readのコード条件は大小文字を区別する完全一致、名称条件は大小文字を区別しないliteral部分一致である。Agentだけの処理を変えたことを、左ペインの検索も変更したと報告しない。
- 回答の同じ文は、一般的な `QUESTION_NOT_ANSWERED` と、範囲の判定結果 `OUT_OF_SCOPE` / `QUESTION_SCOPE_UNCONFIRMED` が同時に生成することで重複した。画面が同一の応答を二度受信したと確認されたわけではない。

## 実装した修正と検証

範囲判定による説明を生成する場合は、一般的な「質問に答えられない」という説明を追加しない。異なる理由・根拠を文字列だけで一括して消す修正ではない。

既存の対応外試験と、範囲不一致・対応外・不確実の試験に重複防止の検査を追加した。ケースの追加・削除・期待する判定の緩和はない。既存イメージへ現在のコードをmountし、Docker内で `backend/tests/agent/test_grounded_answer.py` を実行：**22成功、失敗0（0.31秒）**。これは全Backend試験、実モデル、実ブラウザの結果ではない。新規イメージは作成していない。

## 表記照合の置換方針

候補文字列を個別に増やす方式を、登録データとの照合へ置き換える。以下を実装上の判断基準とする。

1. 原文・登録値は保持し、比較用のキーと区別する。Unicodeの互換・結合表記と文字の大小は共通の正規化規則として扱う。コードの先頭ゼロ、区切り、文字の脱落、意味の同義関係まで同一視しない。
2. 数の表現は、コードの識別子と、名称中の数の表現を分けて扱う。既存の数字表記の回帰を削除して置換成功とせず、日本語の語の一部を無条件に数へ変える処理にも置き換えない。
3. 元の表記で一件見つかっても、同じ比較キーに別の登録IDがあれば自動確定しない。同じIDの再取得と、別IDの衝突を区別する。LLMの同一設備という申告を証拠にしない。
4. `search_equipment` の既存契約を黙って変更しない。既存のページ取得による登録値との照合は候補だが、12 Tool呼出しの上限を維持し、続き・失敗・予算不足を0件や一意確定にしない。全件走査を無制限に増やす方式は採らない。検索側の契約拡張が必要なら、その変更を別に明示する。
5. 取得結果・Evidence・traceを保持し、回答には実際に対応した設備の登録名・コードを使う。他の設備の取得値を質問への答えとして表示しない。

上記は調査時の判断基準。実装した照合方式・数表現の適用境界は、後述の追加実装とapi-tools §15に記載する。

## 試験の扱い

既存の有用な質問・表記・衝突・ページングの回帰は残す。既存H6-Rの追加自動6件・新留出6種類（総67種類）案は、承認済みの13自動・44実行の枠と区別する。表記照合を含めた必要ケースを再整理してから追加する。既存試験へのassertion追加を、新しい同値クラスの確認済みという主張に使わない。追加の実モデル実行も行っていない。


## 追加実装：検索層への共通化

- 新しい `filter.reference` を既存 `search_equipment` に追加。名称の正規化後部分一致、コードの正規化後完全一致を同じDB条件でOR照合する。従来の厳密な `equipment_code` とliteral `name`、複数filterのANDは維持する。これは既存Tool引数の追加であり、新HTTP経路・DB列・別名機能の追加ではない。
- Unicode NFKCとcasefoldを入力だけでなくDBの登録値にも適用する。任意の大文字／小文字混在や、結合文字・全角半角を、モデルを使わず照合する。コードのゼロ埋め・区切りは残す。
- 名称の明示的な整数の序数表記は、共通の純粋な規則で照合パターンを生成する。任意の日本語の漢字を数値化せず、`第`に続く標準的な0〜9999の整数に限る。複数の数は各トークンで照合し、表記候補の直積や複数HTTP要求を作らない。`第1`が`第11`の数の一部へ一致しない。特定の設備名・コード・質問文は規則に含めない。
- Agentの数表記の候補生成とFrontendの `referenceVariants.ts` を撤去。左ペインとH6の対象照合は同じreference検索を使う。旧通常Readでモデルが厳密条件を使った場合も、共通検索の一回の追加照合へ寄せ、元の実検索のEvidenceを残す。
- 原文・登録値は保存したまま、比較にだけ正規化を使う。DBが実IDを返し、Agentは検索の全ページが揃い実IDが一つの場合だけ対象を確定する。規則の一致を、別IDを同じ設備へ統合する根拠にしない。

### 試験設計・現在の結果

新規は実DBの6件。全直積を作らず、独立した文字・数・識別子の同値クラスと、境界・近傍の対照を選んだ。設備例に依存しない別の名称・コードを使用する。

| 試験 | 防ぐ失敗 |
|---|---|
| 幅・英字大小・前後空白とゼロ埋めの対照 | 登録側の大小混在の取りこぼし、別コードへの混同 |
| カナ幅・結合文字・大小と非同等文字の対照 | ASCIIだけの変換、結合文字の取りこぼし |
| 二つの数の表記が混在する名称 | 一つの数だけの特例、候補の直積・混在表記の取りこぼし |
| 1と11の最小対 | 数の接頭部分による別設備への誤一致 |
| 検索記号を含むliteral名と近傍名 | `%`・`_`・正規表現の記号を検索構文へ昇格すること |
| 別IDの衝突・二ページ・cursor拘束・厳密条件 | 先頭行への自動確定、別filterでのcursor流用、既存AND契約の変更 |

既存の数字表記・複数対象・異なるIDの衝突・取得失敗・ページング試験は残した。旧候補展開の件数・条件文字列へのassertionは、新しい共通検索の呼出しと、元のID・判定・Evidenceの検査へ変更した。候補数・対象ID・曖昧さ・失敗のassertionは弱めていない。
