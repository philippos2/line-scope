# 曖昧な質問解釈の確認設計（#276・文書のみ）

開発者はClaudeとの相談後、確認は解釈が曖昧な場合だけ、口語の全てには挟まない、口語全般の理解は約束しない、曖昧の定義と「違う」の行き先を実装前に明記する方針を採用した。具体設計は[grounded-answer-plan §13](../design/grounded-answer-plan.md#13-h6曖昧な解釈の確認採用方針実装承認待ち)。これは実装承認ではない。

- 「曖昧」はLLMの確信度で決めず、全文が定義へ対応しない、未説明部分が残る、意味の競合、型・時制等を確定できない場合とする。対象の未特定・検索失敗・非対応とは分ける。部分文字列の実在だけを意味の証明にしない。
- 「違う」は原文を残して編集へ戻す。終了通知の失敗で編集を止めない。違うという操作で未登録・非対応とは断定しない。
- 受理は、利用者が選んだ限定的Readとして実行し、元の問い全体に答えたことにはしない。確認は業務承認・実行・運転許可ではない。
- 技術フラグは通常分類から外すが直接Readと技術情報は維持する。embedding・新モデル・追加照合段は入れない。
- 現行のAgentInputでは確認操作を受け取れない。既存POST /agentへ任意の確認choiceと応答を追加する契約案を明記した。新HTTP経路・新DB・認可変更は追加せず、既存の利用者所有・TTL付きConversationStoreを再利用する。原文hashの拘束、現在の対象と権限の再確認、Prepare経路と分離する設計を置く。
- 追加工数は3〜5作業日の暫定値。旧Hの7〜10日とは別。時間軸ガントへ承認U0を起点とする上限5日の配分を追加した。H→F2→F3の3PRを維持する。
- 試験の追加案は自動12＋ホールドアウト6、総54種類。調整6＋評価6を各3回、旧ブラウザ8項目を1回で44項目実行。追加試験も承認待ちで、今回は実行しない。確認率は分母付きで報告し、口語全体の上限は測定後のPO判断とする。

requirements、acceptance-criteria、agent-design、api-tools、frontend-console、evals、roadmapとガントを責務に沿って更新する。旧い拒否・確認省略の方針は、現行実装の記録と新しい設計案を混同しないよう置換範囲を明示した。原文と照会範囲を分離することは、自然言語の誤解がゼロになったとの主張ではない。
