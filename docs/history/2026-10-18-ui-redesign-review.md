# UI再設計のレビュー準備

## 指摘と方針

PR #262 merge後の利用者確認で、設備探索を算定データに依存させた入口、依存関係の調査を別モードへ分離したこと、不自然な文言について指摘された。代表試験の成功をUI設計の妥当性として扱った判断を撤回する。機能実装の到達点と、利用者が自然に目的へ到達できるかは別に評価する。

開発依頼者から提示されたClaudeの指示書を基に、まず文書として設計を作り、Claudeの評価を受ける指示となった。Frontendには着手しない。

## 今回の成果物

[UI再設計案](../design/frontend-redesign-proposal.md)に、目的、画面構成、操作順、状態別表示、データ経路、責務、移行表、用語、UA-01〜08、判断待ちをまとめた。現行画面設計には案へのリンクだけを追加し、新設計へ置き換えていない。

現行APIとコードから、非LLM設備検索の経路が未決であることに加え、現行損害額算定は稼働中設備の仮想停止金額を扱わないことを確認した。候補すべての算定データ有無も一括取得できる契約ではないため、案では未確認と未登録を区別し、判断点として明記した。

## 変更しない範囲と次の工程

Frontendソース・Backendソース・API契約・データ・稼働サービスは変更しない。文書リンクと差分を確認し、実装のテストやサービス再起動は行わない。

次はClaudeと開発依頼者による設計評価。設備検索経路等の未決事項と設計の承認後に限り、実装を開始する。本書作成は実装許可ではない。

## Claudeレビューを受けた設計書改訂

開発依頼者からM1〜M6の改訂指示を受け、コードを再確認した。変更は設計書と本履歴のみ。実装・データ・API契約・稼働サービスへは着手していない。

- M1：登録上の状態を表示し、稼働中の対象外理由、保全中・不明の適用未確認を状態表へ追加した。稼働中ではAPIに不足理由がないため、返却状態から表示理由を決める。
- M2：未決中の見出しを登録状態に基づく算定へ合わせ、D2(a)/(b)を併記。どちらも採用確定していない。表示マッピングは集約するが、(b)は文言変更だけでは実現しないと明記した。
- M3：私のequipment_query前提は誤りだった。equipment_idの完全一致フィルタがあり、選択設備にはそれを使う。候補バッジは絞込みなし検索のequipment_id集合から判定する案へ訂正した。page_size上限100、ページ追跡、検索行にpayloadがないこともコードで確認した。前節の「一括取得できる契約ではない」は設備検索自身に属性がない点だけに当たり、経済入力検索の一覧で補える。
- M4：評価期間は読取専用へ変更。入力期間の不一致では、該当設備・入力・期間と登録・訂正導線を示す。
- M5：算定データの存在と損害額の登録を分け、未登録状態を追加。計上項目なしでは金額を出さず、根拠付きの明示0は区別する。
- M6：UA-09〜12を追加。稼働中・保全中・不明・損害額未登録・期間不一致と、再現データを実装前に明示する条件を加えた。

照合したコードはmainのfc9e4fbと同じ内容。application/economics.py、persistence/core_economics.py、domain/incident_loss.py、application/incident_investigation.py、application/graph_analysis.pyを参照した。

レビュー説明との相違は小計の応答値。incident_loss.aggregateは内部の加算を0で開始するが、included_in_subtotalが真の範囲がない場合、known_subtotal_per_hourはnullを返す。「未登録だから判明分0円」とはならないことを設計書にも記した。未登録時に金額を表示しないという要求は維持した。

D1・D2は未決、D3・D4はオーナー確認待ち。変更計画・設計の承認を待ち、まだ実装しない。文書リンクと差分だけを検証し、実装テスト・サービス再起動は行わない。
