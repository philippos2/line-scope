# LineScope 文書レビュー

レビュー日: 2026-10-09

本書は初回レビュー時点の記録。指摘への修正・確定方針・未解決事項は[文書修正・セルフレビュー報告](2026-10-09-documentation-update-report.md)を参照する。

## 1. 対象と結論

`deliverables.md` を起点に、同書が定義する19文書すべてを読んだレビューである。実装は行わず、既存のコード・設定・文書は変更していない。本書は追加のレビュー記録であり、仕様の正本を変更するものではない。

全体方針は一貫している。一方、安全性・業務判定に関わる不整合や未定義事項があり、推測なしに全体を実装できる状態ではない。

## 2. システム全体の理解

LineScopeは、製造設備・保全・生産運用の情報を自然言語で参照し、依存関係を分析し、承認付きで更新するシステムである。v1は単一工場、UIなし、HTTP API / curl中心。

| 経路 | 処理 |
|---|---|
| 参照 | Agent → Read Tool → PostgreSQL → 回答 |
| Graph分析 | Agent → 同期確認 → Neo4j探索 → 構造化Evidence → 回答 |
| 更新 | AgentによるPrepare → 人によるApproval API → 元requesterによるExecute API |

AgentはIntent分類、情報収集、Tool選択、結果説明を担当する。認証、認可、承認成立、確定更新はサーバ側の責務。Graph Evidenceもサーバが構築し、LLMの説明と分離する。

## 3. 文書群の責務境界

[deliverables.md](../deliverables.md) の責務表は、単純な上下関係ではなく事項ごとの正本を指定している。

| 文書群 | 責務 |

| requirements | 業務上何を実現・禁止するか。業務概念、Graph意味論、権限、承認、受入条件 |
| design | 構成要素の責務、Agent実行設計、DB・Graphの物理モデル |

Graphの意味論はdomain-model、物理Projectionはdata-model、同期・Lockはtransaction-design、入出力はapi-toolsが正本。実装設計が業務要件を暗黙に変更することは認められていない。

## 4. データストアの責務

| ストア | 責務・正本性 |
|---|---|
| PostgreSQL | 業務データ、設備状態、Equipment割当、更新要求、承認、履歴、Outbox、KnowledgeDocument metadataの正本 |
| Neo4j | 依存関係探索用の派生Read Model。設備状態等は複製せず、必要時にPostgreSQLを参照 |
| Qdrant | マニュアル・保全手順等の派生Vector Index。検索後にPostgreSQL metadataで再認可 |

文書本文の正本は管理対象ファイル。Neo4jとQdrantは正本から再構築可能である必要がある。

ProductionOperationのEquipment割当はProductionOperationEquipmentAssignmentだけを正本とし、Neo4jのUSESを派生させる。単一Equipment FKやDependencyRelationへの二重保持は禁止。

## 5. Approval / Execute / Outboxと更新Transaction

1. Prepare: requester認可、対象一意化、現在値取得、変更予定Snapshot生成、hash生成、更新要求とPENDING承認を保存。業務データは変更しない。
2. Approval: 認証済み承認者が保存済みSnapshotを確認し、そのhashを専用APIへ送る。成立から30分有効。
3. Execute: 認証済みの元requesterだけが専用APIで開始する。
4. Transaction: 必要なGraph mutation lock、更新要求・承認の行ロック、期限・hash・version・業務制約の再検証、全Target更新、履歴・Outbox保存、承認消費、COMPLETEDを同一Transactionで確定。
5. Projection: commit済みOutboxを単一active workerがNeo4jへ反映する。

COMPLETEDはPostgreSQLへの確定完了であり、Graph反映完了とは別である。

一時的なcommit前障害ではROLLBACKし、承認を再利用可能にする。version・業務制約競合等では別Transactionで承認を失効させる。COMPLETEDのExecute再送は既存結果を返す。

## 6. Graph同期状態

[transaction-design.md](../implementation-design/transaction-design.md) の優先順位は以下。

| 優先順 | 条件 | 状態 |
|---|---|---|
| 1 | rebuild flagあり | REBUILDING |
| 2 | DEADあり | ERROR |
| 3 | PENDING / PROCESSING / RETRYABLEあり | LAGGING |
| 4 | 上記なし | CURRENT |

採番順をcommit順とみなさず、commit済みイベントの状態集合で判定する。Neo4jへの反映はaggregate versionで古いイベントを拒否し、同versionの再適用を冪等にする。

Graph分析はCURRENT時のみ正常利用可能。探索上限に達した一般探索は部分結果、SPOF判定はINDETERMINATEを返す。

## 7. 不整合・手順上の問題

### F-01 未承認要求の期限が未定義

承認期限は「承認成立から30分」で、expires_atもapprove成功時に設定される。一方、approve時の期限検証、PENDING → EXPIRED、WAITING_APPROVAL → EXPIRED、approve期限境界テストが定義されている。

未承認要求の有効期限・起算点がないため、これらの判定を実装できない。

参照: [access-control §6](../requirements/access-control.md)、[transaction-design §3・12・13](../implementation-design/transaction-design.md)、[test-plan §3](../implementation-design/test-plan.md)。

### F-02 Rebuildでworker停止後にOutboxを空にする

手順は「Projection worker停止 → mutation lock取得 → 未処理Outboxを0にする」。停止したworkerに代わって誰がイベントを適用するかがない。未処理イベントがある場合、そのままでは進めない。

参照: [transaction-design §11](../implementation-design/transaction-design.md)。

### F-03 worker重大障害のERROR判定が実装設計にない

architectureはDEADだけでなくProjection worker重大障害もERROR条件にする。しかしtransaction-design、data-model、operationsの判定表にはその条件がない。障害を表す状態、検出方法、復旧条件が必要。

参照: [architecture §7](../design/architecture.md)、[transaction-design §10](../implementation-design/transaction-design.md)、[data-model §6](../design/data-model.md)、[operations §3](../implementation-design/operations.md)。

### F-04 requiredの説明とSUPPLIESの意味の不整合

required=trueは「sourceの成立にtargetが必須」と定義される。一方、SUPPLIESはsourceがtargetへ供給する関係なので、必須供給ならtargetの成立にsourceが必要と解釈される。関係種別ごとのrequiredの意味を明確にする必要がある。

参照: [domain-model §4・7](../requirements/domain-model.md)。

### F-05 Snapshot変更による失効と状態遷移の範囲

UC-13は承認対象変更時のINVALIDATEDを要求するが、状態遷移表にはWAITING_APPROVAL / PENDINGからINVALIDATEDへの遷移がない。UC-13が承認成立後だけに適用されるのか、Snapshotを変更可能にするのか、常に新規UpdateRequestを作るのかが未定義。

参照: [use-cases UC-13](../requirements/use-cases.md)、[transaction-design §12](../implementation-design/transaction-design.md)。

### 閲覧権限についての補足・訂正

会話中の初回レビューでは、更新要求の閲覧権限を問題として挙げたが、単一カテゴリの現行承認経路が成立しないという矛盾は確認できない。

- 設備状態を承認する保全担当者は、設備状態関連の更新要求を閲覧できる。
- 生産運用を承認する生産管理担当者は、生産運用関連の更新要求を閲覧できる。
- 依存関係を承認する工場管理者は全件閲覧できる。
- requester本人は自身のUpdateRequestを参照できる。

保全・生産管理担当者が他人の依存関係要求を閲覧できないこと自体は、現在の承認権限と矛盾しない。残る論点はU-05とU-20であり、これを明確な矛盾とは扱わない。

## 9. 実装前の優先確認事項

設計の中心であるPostgreSQL正本、派生Graph / Vector Index、承認と実行の分離、全Targetの原子更新、Transactional Outbox、非CURRENT時のGraph拒否は明確。受入基準と決定論的テストの対応も整理されている。

実装前に特に確定すべき事項は、承認前の期限、requiredとSPOFの業務意味、更新の並行制御、Graph分析の整合境界、RebuildのOutbox処理、Snapshot・冪等性契約である。これらは実装者の選択によって承認内容、更新結果、分析結果が変わるため、推測で補うべきではない。
