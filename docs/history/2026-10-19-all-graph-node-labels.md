# 関係図の全ノードの名称取得と表示

## 現象・原因と着手前報告

開発依頼者から工程・生産作業が「名称を確認」のままと指摘を受け、修正前にコードと実ブラウザを確認した。M-204の表示8ノードのうち工程2件・生産作業2件が未取得だった。旧実装は製品・候補設備・インフラだけを名称の自動取得対象にしていた。DBに工程名・作業コードは存在しており、APIやデータの欠落ではない。既存のブラウザ確認がこれらのラベルを検査していなかった。

同じPR #265のFrontend修正で対応できることと、取得方法・上限・表示案を作業前に報告した。インフラ状態の機能拡張は行っていない。

## 修正

- 関係図に表示する設備・工程・生産作業・製品・インフラを、既存get_*の直接経路で取得する。下流・上流・代替を重複排除した共有キューへ載せる。詳しい分析で表示するノードも同じキューを使う。
- 起点ごと最大100ノード、同時4件。取得できた順に図と一覧へ反映。上限は明示し、無制限取得しない。新しい一括取得ToolやAPIは追加しない。
- 設備・工程・製品・インフラは「名称 · コード」。名称末尾に既に同じコードがある場合は表示上の重複だけを避ける。生産作業には名称フィールドがないので作業コードで表示。工程は別ノードで分かるため工程名を重複併記しない。
- 取得中は読み込み中、失敗時は名称取得に失敗と再試行。表示済みの関係・金額を残し、名称だけを再試行する。既知のコードがあればコードを表示する。初回取得失敗でtyped IDしかないときは業務コードを捏造しない。
- 起点のAbortSignalで未実行リクエストと古い成功・失敗の反映を止める。名称読取では応答のIDとコード項目も照合する。一般の依存設備を代替候補として登録しないよう、候補集合との照合を維持する。
- 図とアクセシビリティ一覧の表示を統一。「名称を確認」「名前を確認」を通常表示の禁止語へ追加。

## 検証

- Docker内npm run check成功。lint・型・format・buildを確認。既存の500 kB超bundle警告あり。
- Unit：既存Graph表示10件＋提案表示8件＋名称キュー1件＝19件成功（617ms）。キューの1件は、上限・同時実行・重複・失敗→再試行→起点中断の状態遷移を検証する。既存の親Processを取り違えないテストも名称・コードと作業コードの表示を確認するよう強化。
- 実ブラウザ：11項目成功。通常の図と一覧で全ノードの名称または作業コードを確認。390pxの切替では金額に加えて工程名の実応答も遅延させ、旧ラベルが新しい起点へ混ざらないことを確認。
- 制御応答の名称失敗を1項目追加。工程のgetを失敗させて図・一覧の失敗表示を確認し、実APIへの再試行で名称が復旧し、表示済み200000円／時間が保持されることを確認。
- PR全体の追加検証はUnit 9件＋ブラウザ11項目＝20。既存10件は追加数に含めず、ケース分割や直積の増加は行っていない。
- 名前検索は67ms、選択から主要結果まで553ms（今回の1回の観測値でSLAではない）。スクリーンショットは.git/verification/scenario1-labels配下に保存し、実画像を確認した。
