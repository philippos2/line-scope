# Graphを中心から外したUI設計と誤った完成報告

## プロダクトの目的

LineScopeは、設備・工程・生産作業・製品・インフラ等を、業務上の意味を持つ関係で結ぶライトウェイト・オントロジーシステムである。ノード間の関係を可視化し、起点から他のノードへ及ぶ影響範囲と根拠経路を特定する。状態取得・比較・文書検索・承認付き変更は、その理解と判断を支える。

目的の正本はrequirements §1、R-07〜R-15、§13、関係の意味と方向はdomain-model §4〜6。従来のfrontend-consoleもGraphを中心にObject／Evidence／Actionを関連付ける設計を明記していた。文書がなかったことを原因にはしない。

## 失敗した判断・報告

- 代表API経路とCIの成功を、常設環境とUIを含むプロダクト全体の完成へ拡大し、「100%」「追加機能PR 0」と報告した。常設のQdrant接続・文書投入、UIの一連操作と分かりやすさを確認していなかった。
- UIから全工程を通した事実がない段階で理想のシナリオを列挙し、既存画面で操作できる範囲と混同させた。
- UIの分かりにくさへの対応として6工程の画面へ再構成したが、Graphを調査工程の一表示へ閉じ込めた。ノード間の関係・他の設備や工程や製品への影響を理解することより、個別機能を順番に操作することを主役にした。
- 下流Graphを描画し通し試験が成功しても、それだけではGraph中心の調査体験を実現したことにはならない。この目的との照合を実装前と受入時の判断に使わなかった。
- 作業ブランチでは画面設計文書も6工程中心へ変更した。実装に合わせた文書変更で、上位要件との不一致を解消した扱いにしてはいけない。
- 結果として、開発依頼者に目的と優先順位を繰り返し説明させ、時間と資源を費やし、UIの手戻りを生んだ。モデルのバグや開発依頼者の説明不足と断定できる根拠はない。

## 検証できたこと・できていないこと

- 全必須部品の常設接続は進めた。PostgreSQL・Neo4j・Projection・Qdrant・API・Frontend、ホストOllamaのLLM／Embeddingを使用。デモ文書を取り込み、ブラウザでsource QDRANT、demo_only false、引用1件を確認した。
- 6工程版source a2a6fecの常設UIでは、設備選択・状態・下流6件・未選択比較・文書引用・経済入力準備・別manager承認・元manager実行・再比較の10段階が成功した。Frontend既存Unit 27件とlint・型・format・buildも成功した。
- 上記は機能接続と1代表シナリオの成功であり、目的にかなうUIであるという開発依頼者の受入、全BS、全更新variant、任意自然文の精度を確認した意味ではない。
- API・FrontendのHTTP200だけで「画面が表示できる」と報告したのも確認不足だった。描画・接続・実操作を実ブラウザで確認する必要があった。
