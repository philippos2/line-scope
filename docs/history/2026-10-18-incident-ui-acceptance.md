# P2：工場トラブルのUIと実機検証

## 依頼と到達点

PR #261のmerge後、ロードマップP2として、二台の機材トラブルを対象に影響範囲と時間当たり損失を同じ流れで把握できるUIを実装した。機能追加・画面・検証・操作文書を一つのPRにまとめる。

- 新しい入口で対象設備・正式な経済入力・評価期間を明示的に選ぶ。
- 取得した設備別経路をまとめ、影響Graphと推定被害額を隣接表示する。設備別表示、ノード選択、経路強調も保持する。
- 内訳・出典・重複排除・不足理由を示す。金額はサーバの応答を表示し、Frontendで合算しない。未算出と0を区別し、大きな金額の表示でもNumber変換で精度を落とさない。
- Graphを保持して対応案比較・実文書の引用・入力訂正へ進む。経済入力の損失範囲と出典を保持したまま率を訂正できる。
- 設備カードから変更後の登録状態を明示選択し、変更準備へ渡す。別managerの承認と元requesterの実行を経て再調査する。
- 対象・期間変更時は前の結果を消す。実行後は金額を未算出にして再取得を案内する。比較対象切替時は別設備の変更下書きを破棄する。

従来の設備単位の調査、共通依存・代替・SPOFの分析は保持した。取得候補は経済入力検索の先頭10件であり、工場全体の網羅一覧・自動異常検知として扱わない。

## 実装時の修正

Graph属性の照合で、生産作業の外部キーprocess_idが工程自身のIDとして一致していた問題を修正した。get/searchの対象型とIDを照合し、別種のレコードの属性を流用しない。

初回ブラウザ試験では、状態変更用文の固定構文と試験locatorに不一致があり停止した。設備カードからの明示選択とselectのラベルを揃え、再実行した。途中で確定した損失率の訂正は、同じ承認付きUIから戻した。最終lintでも試験内のdocument参照の宣言漏れを検出し、修正後にcheckを再実行した。失敗を合格に含めていない。

## 検証

- Docker内のnpm run check：lint・型・format・build成功。bundle 536.83 kBに対するViteの500 kB警告あり。今回は分割最適化を追加しない。
- 金額の正確な表示と型を跨ぐID照合に絞ったUnit Test：2ファイル12件成功、465ms。新規追加は3件で、既存9件を含む。
- 実ブラウザ：PostgreSQL・Neo4j・Embedding・Qdrant・APIへ接続し、下記10工程を成功。mock応答は使わず、browser runtime errorは0件。
- 390／768／1600pxで横overflowなし。Graphと金額の配置・経路選択も画面で確認。
- Backendコード・契約・migrationは変更していないためBackend試験は追加実行しない。CIの対象判定と最新headの結果はPR本文に記録する。

## 常設環境と再開

- 専用Compose project：linescope-incident-demo。APIはhttp://127.0.0.1:8000、Frontendはhttp://127.0.0.1:5173。
- 私有設定はRepository直下の.env.incident-demo（Git対象外、mode 0600）。旧デモの認証設定も保持し、従来のtokenで接続できる構成にした。認証値は文書・PRへ記録しない。
- seed-demo-incidentで投入し、Graph再構築・Projectionと実文書取り込みを実施した。新規データ専用のDB／volumeを維持する。
- 起動はdocker compose -p linescope-incident-demo --env-file .env.incident-demo -f compose.yaml -f compose.frontend.yaml -f compose.rag.yaml --profile frontend up -d --wait api frontend projection。
- 旧linescope-browser-demoはAPI／Frontendのみ停止した。旧DB・volume・設定は削除していない。
- 通常ポートへの切替後、読取だけのブラウザ確認で入口→二台選択→影響製品3件・250,000円／時間を再確認した。

実測log・画面・reportは.git/verification/incident-ui/に保存した。ブラウザ試験用認証ファイルと専用検証imageは引渡し前に片付け、常設環境の設定とデータは残す。
