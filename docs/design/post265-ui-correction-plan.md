## 3. 上部タブの構成

Claudeの推奨に沿う統合改修案を§11にまとめた。現段階でレビューする構成は次のとおり。

```text
LineScope 設備調査                              接続設定
[接続及び影響範囲][対応案を比べる][質問する][出典と経路]  [入力を登録・訂正][変更・承認・実行]
要約帯：起点 第1加工機 · M-204（登録上：停止中）[変更]
        損害額 200,000円／時間 ｜ 候補 M-208 利用可能・P-100のみ能力充足 ｜ 調査取得時刻

各タブの見出し：このタブが実際に扱う対象・入力・期間・結果・要求ID
タブの内容
```

6タブは同じ階層のままとし、「調べる・判断する・記録変更する」は責務の分類だけに使う。画面上で新たな階層・モード切替は増やさない。初期表示は「接続及び影響範囲」。要約帯は調査の文脈と重要な判定を示し、入力レコードや保存要求の対象を上書きしない。狭い画面では折返し等により全タブへ到達可能にする。

## 4. コード照合と修正方針

### 4.1 比較と関連文書の対象設備

`frontend/src/app/App.tsx`は、調査設備変更時に`decisionEquipment`をnullへ戻す。比較対象が設定されるのは、右欄の「この設備で対応案を比べる」等の明示操作時。下部タブを直接開くだけでは設定されない。

`RegisteredComparison.tsx`の候補取得ボタンは比較対象未設定で無効になる。関連文書検索も`decisionEquipment`を条件にしている。このため設備を検索・選択しただけでは両方が無効のままになる。

対応案は、調査中の設備を対象にする明示操作を各該当タブから利用できるようにすること。文書検索は文書検索の対象を表示し、比較という別機能の操作を先に要求しない。対象未選択・処理中・権限不足・検索先の接続不良を区別する。

### 4.2 比較期間の導出と日時選択

現コードの開始・終了はtimezone付き文字列を直接編集するinput。今回の改修案では、**比較タブの期間は選択入力から導出して読み取り専用、DatePicker等の日時選択は入力の登録・訂正へ置く**。

- 経済入力を選択している場合はその期間を基準とし、なければ選択した能力・保全計画の期間が全て一致する場合に共通期間を表示する。
- 比較対象期間を一意に決められない場合は自動で仮定せず、期間を持つ入力の選択または登録・訂正へ案内する。
- 経済・能力・保全計画は完全一致、安全入力は比較期間全体の被覆を必要とする。故障・修理履歴は過去の背景情報であり一致条件から除外される。共通期間の導出元にしない。
- 不一致なら入力ごとの対象・コード・期間を表示し、入力の選び直し・訂正へ導く。期間の交差・丸め・自動変更で一致したことにしない。
- 登録・訂正の日時選択は日本時間と明示し、timezone付きAPI値に変換する。未編集時の秒・小数秒は保持し、表示しただけで元の値を変更しない。
- 開発依頼者の元の要望は日時を選べる入力であり、業務上任意の比較期間を許可するとの決定ではない。今回の配置案では、期間を新たに作る登録・訂正画面で要望を満たす。

### 4.3 入力登録・訂正の候補

対象は4カテゴリの検索・作成・訂正にある入力欄。現状の各Panelとその編集部品を棚卸しして、フィールドごとに候補取得元・入力方式・検証規則を対応づけてから実装する。

| 欄の種類 | 設計方針 |
|---|---|
| 名称・コード・出典等の文字列 | 既存の登録内容等に由来する候補を選べ、候補外の値も手入力できる。候補の根拠と取得範囲を定める |
| 設備・製品等への参照 | 人が名称・コードから選べるようにする。自由入力は検索語として扱い、存在しないIDを推測・生成しない |
| 数量・金額・単位 | 手入力と候補選択の両立を検討する。値を架空の既定値で埋めず、型・単位・未知の扱いを維持する |
| 日時・期間 | 日時選択と手入力の扱いを整理し、timezone付きAPI契約を維持する |
| 真偽値・種別など契約で値が限定される欄 | 許可値の選択と入力補助を提供する。候補外の任意値を受理するよう業務契約を変更しない |

§9の調査で、登録済み値を候補にするための既存検索・詳細APIは確認した。専用の候補辞書・自動採番APIは今回確認しておらず、その追加を前提にしない。足りない場合は必要な変更を報告してから判断する。M-204/M-208や固定金額の専用候補を埋め込まない。未選択・不明・0は区別し、候補の選択だけで変更を確定しない。

### 4.4 変更・承認・実行

現状には次の無効条件がある。§9で初期状態と有効化経路を実画面で確認したが、開発依頼者が操作した全状態を再現したわけではない。

| 操作 | 現在の無効条件の例 |
|---|---|
| 登録状態の変更下書き | 変更後の状態が未選択 |
| 変更準備を作成 | 指示本文が空、または処理中 |
| 保存状態を再取得 | 要求IDがUUID形式でない、または処理中 |
| 承認・拒否 | 保存内容の確認未チェック、有効性条件未充足、承認待ちでない、処理中 |
| 実行 | 保存内容の確認未チェック、有効性条件未充足、承認済みでない、処理中 |

実装着手後、実画面の操作・返却状態・権限を照合して原因を特定する。無効条件は理由と次に必要な操作を示す。Prepare→別担当者のApproval→元依頼者のExecute、期限・version・Snapshot・再送キー等の制約を外して有効化しない。

### 4.5 質問機能

LLM接続の復旧と今回のUI改修を分ける。5174番は既存Ollama/Qwenへ接続を復旧し、実質問がHTTP200/status okで回答することを確認済み。残るのは選択設備の引継ぎと原因別エラー表示。

「この設備」の質問対象を画面で明示し、設備を切り替えた後に旧設備の会話が新設備へ混ざらないことを確認する。既存の設備・権限・確定操作の契約を変更しない。

## 6. 確認項目

- 6タブが上方の同じ階層にあり、改称が反映される。390／768／1600pxとキーボードで操作できる。
- 設備未選択・選択済み・設備切替の各状態で、対象の案内とボタン状態が一致する。
- 比較タブ内から対象を指定し、候補取得→入力選択→共通期間の表示→比較結果へ進める。
- 登録・訂正の日本時間の選択とAPIのtimezone付き日時が往復で一致する。登録期間が合わない場合は理由が分かる。比較タブの期間は読み取り専用で、日時選択は入力登録・訂正にある。
- 比較対象を設定する前でも、文書検索の対象指定から検索を実行できる。出典・経路は表示を主とし、編集は入力登録へ分ける。
- 各入力欄で、手入力と候補選択、候補なし・検索失敗・不正値を確認する。候補外の値の扱いは欄の契約に従う。
- 変更準備→別担当者の承認→元依頼者の実行を実画面で確認する。無効時の理由と次の操作が分かる。
- 質問対象の設備が明確で、切替・遅延応答・接続解除で旧結果が復元されない。LLM障害等の案内が原因に合う。
- 文書作成時点では上記の改修・受入を実施していない。追加試験は実装前に件数と範囲を見積もる。

## 9. 深掘り調査の結果と限界

### 9.1 実画面の変更操作

5174番に工場管理者として接続し、既存ブラウザ検証イメージを再利用した。新規イメージは作っていない。変更要求作成・承認・拒否・実行のリクエストは送信しないよう遮断した上で、表示とローカル入力を確認した。遮断に該当する送信自体も発生していない。

| 設備未選択で変更タブを開く | 「変更準備を作成」「保存状態を再取得」は無効。状態変更の欄はない | 対象・本文・要求IDがない初期状態 |
| M-204を選び変更タブへ移る | 「変更の下書きを作る」も無効、指示本文は空 | 変更後状態の選択が必要だが、次の操作の案内が不十分 |
| 変更後状態を稼働中にする | 下書きボタンだけが有効になる | 状態選択から下書きへは接続している |
| 下書きボタンを押す | 指示本文が入り「変更準備を作成」が有効になる | 準備ボタンが常に壊れているわけではない。下書き→サーバへの準備依頼という2段階が分かりにくい |

修正の中心は対象・変更内容・下書き・準備済み要求の段階を明示すること。初期状態や無効ボタンの近くに「変更後の状態を選んでください」「下書きから変更準備を作成してください」「要求IDを入力してください」等、現在不足する条件を表示する。承認・実行は保存済み要求の状態と操作主体を表示し、正当な制約を外さない。

### 9.3 欄ごとの制約

- 既存登録の値は参考候補であり、推奨値・適用可能な安全条件とは限らない。候補には対象・出典・適用期間等を示し、利用者が明示選択する。安全条件や費用を自動で充足済みにしない。
- 入力コードは作成時の識別子。既存コードを候補としてそのまま新規登録すると重複し得る。訂正では既存の設備・入力コード等は変更不可で、payloadのみを変更する契約がある。候補対応のためにこれを解除しない。
- 種別・判定・確度・真偽値は既に選択UIがある。自由入力を加えるために許可値を拡張しない。
- 製品・保全予定は既存参照から選択し、未知のIDを生成しない。数値は手入力可能とし、候補なしを0にしない。日時は日時選択の設計を共通化する。
- 新規採番の自動化、全社的な候補辞書、未登録の安全・保全情報の追加は本調査で実現していない。必要だと判断した場合は範囲を別途確認する。

### 9.4 工数評価と調査終了

現在の証拠では、既存の契約を維持したFrontendの導線・候補表示の改修が中心であり、DB・承認処理の作り直しや候補専用APIを必須とする根拠はない。調査時点では基本2 PR・4〜6作業日とした。その後の要約帯・ドロワー追加を含む現行見積もりは§11.10へ置き換えた。承認・実行の実環境受入と、候補0件のカテゴリの実データ表示は未確認であり、追加変更が不要と保証しない。

開発依頼者の「一定範囲を調べても評価不能なら一旦止める」指示に従い、この範囲で調査を終了した。未確認を埋めるための試験用データ投入・変更要求作成・権限変更は行っていない。実装開始命令までは修正しない。

### 10.2 再配置後に通す操作シナリオ

ボタンが押せることだけでなく、次の連続操作を受入対象とする。

1. 起動→比較タブを先に開く→共通欄で設備検索・選択→比較を進める。設備選択のために図タブへ戻らされない。
2. M-204の関係図→候補M-208の属性確認→M-204への対応案比較→対応する比較根拠→関係図へ戻る。対象と候補を取り違えず、図の結果と位置を維持する。
3. 入力を途中まで編集→他タブへ移動→戻ると保持。設備変更を試す→破棄確認を取り消すと元の編集を継続。切替を確定した場合は旧入力を新設備へ送れない。
4. 入力から変更準備を作成→要求IDを控える→別担当者へ接続切替→設備未選択のままIDを開いて承認→元依頼者がIDから読み直して実行。対象はSnapshotと一致する。
5. 登録期間に秒以下がある入力をDatePickerで表示→未編集で比較。時差・丸めによって期間不一致を作らない。編集して不一致になった場合は原因が分かる。
6. 質問・文書検索の送信→別タブを編集→遅い応答が来る。表示中の編集を失わず、対象を切り替えた後の旧結果が復元されない。

## 11. Claude推奨に沿う統合UI改修案

### 11.1 目的と責務

設備トラブルの影響・損害額・代替を調べ、対応を判断し、必要な登録内容・状態変更を承認付きで行う。単に六つの操作を並べるのではなく、各操作が異なる対象を持つことを画面へ反映する。

| 仕事 | タブ | タブが扱う対象 |
|---|---|---|
| 調べる | 接続及び影響範囲 | 起点設備。図の選択ノードは属性閲覧用として別に保持 |
| 判断する | 質問する | 起点設備と、その設備についての会話 |
| 判断する | 対応案を比べる | 起点設備・代替候補・明示選択した入力・導出した期間 |
| 判断する | 出典と経路 | 特定の調査結果・比較結果・関連文書 |
| 記録する | 入力を登録・訂正 | 新規入力の対象設備、または既存入力レコード。既存入力の設備は変更不可の属性 |
| 変更する | 変更・承認・実行 | 新規変更の下書き、または要求IDから取得した保存済みSnapshot |

### 11.2 情報の塊・タブ順・要約帯

#### 情報の塊と配置原則

一つの判断に必要な結論・根拠・限定を同じ塊に置く。結論→根拠→詳細の順とし、主張と限定を別タブへ分けない。高頻度・高重要の調査情報はタブ1と要約帯、低頻度の書込みは末尾のタブ、内部値・技術情報は各塊の末尾の折りたたみへ置く。低頻度でも承認時のSnapshot・要求ID等の重要情報は、そのタブの目立つ位置に置く。

6タブの順は**接続及び影響範囲→対応案を比べる→質問する→出典と経路→入力を登録・訂正→変更・承認・実行**。全て同列とし、最後の2タブは間隔で視覚的に区切るだけで階層やモードを増やさない。

#### 要約帯の確定4項目

どのタブでも参照できる要約帯を設ける。項目は以下の4つに限定し、今回増やさない。

| 項目 | 表示と限定 |
|---|---|
| 起点 | 名称・コード・登録上の状態。設備検索と候補一覧は左ペインに常時表示し、全タブで共有する。「変更」または未選択時の「設備を選ぶ」は左ペインの検索欄へフォーカスする |
| 損害額 | サーバ返却の金額・円／時間。「判明分のみ」「更新前」は金額と同じ行。未算定・算定対象外は理由を短く表示し、0にしない |
| 代替の可否 | 候補・利用可能性・評価した製品の能力判定。「P-100のみ能力評価」等を判定と同じ行に示す。利用可能かつ能力充足の場合だけ限定した吸収見込みとし、運転許可や全業務の代替可とはしない。利用不可・不明は提案しない理由を示す |
| 取得時刻 | 調査結果の取得時点。更新後は「更新前」。比較・文書・保存要求の取得時刻は各タブに置き、調査の1時刻へ統合しない |

金額の内訳や判定の詳細はタブ1のそれぞれの塊へ置き、要約帯の項目から対応する塊へ移れるようにする。損害額と代替判定の出典・期間・評価対象外の情報は主張から切り離さず、要約時にも誤読を生む限定の省略をしない。

広い画面は1〜2行、狭い画面は1行の表示と展開を用意する。ただし収納幅に収めるために金額や能力判定だけを残して限定を隠さない。収納時は起点と取得状態を表示し、限定ごと収まらない金額・判定は展開後に一緒に表示する。6タブは768px未満でタブ列内の横スクロール、768px以上で折返し等を用い、ページ全体の横スクロールは発生させない。

要約帯は調査の文脈を示す。各タブは自分の対象を見出しに出し、入力レコードやSnapshotの設備を調査起点で上書きしない。起点・候補・閲覧ノードは別に保持する。

### 11.3 各タブの操作

1. **接続及び影響範囲**：起点設備から図・登録状態・推定損害額・代替候補を表示。関係図は上段の広い領域、損害額と代替提案はその下の塊とし、選択ノードの属性は図に隣接させる。候補ノードの属性閲覧では起点を変えない。「この設備自体を調べる」の明示操作でのみ変更する。
2. **対応案を比べる**：「M-204への対応案」と起点を明示し、候補と入力を選ぶ。主画面の選択を比較の初期値へ引き継ぎ、§11.8の条件付き事前選択を全タブで共通にする。期間は§4.2で導出して読み取り専用。版・出典・期間・未選択範囲を確認できるようにする。
3. **質問する**：質問対象の起点設備を表示して送信へ引き継ぐ。起点変更後の会話は旧設備と混ぜない。失敗は原因別に案内する。設備別会話の再開機能は今回追加しない。
4. **出典と経路**：「調査」「比較」「関連文書」を区別する。各結果の「根拠を見る」から、その結果を指定した参照ドロワーを開く（ドロワーはA1の次のA2で実施）。タブを直接開いた場合も現在表示する結果を明記し、未取得の種類は未取得と示す。関連文書検索は検索対象を表示する。
5. **入力を登録・訂正**：新規作成か既存入力の訂正かを明示する。新規作成は対象設備、訂正は入力コード・版・対象設備を見出しに出す。候補付き入力と日時選択を提供する。単位・対象・期間・出典を伴う参考候補として扱い、無条件に推奨値や安全確認済みへ変換しない。
6. **変更・承認・実行**：設備未選択でも要求IDから保存状態を取得できる。対象はSnapshotから表示。準備・承認・実行の段階と操作する人を明記し、無効時は不足条件・次の操作を示す。別担当者への切替前に要求IDを控える操作を提供する。

### 11.4 移動・保持・破棄

| 操作 | 改修案での扱い |
|---|---|
| 同じ起点でタブを移る | 取得結果・比較選択・編集内容・図の位置を保持する。戻るだけで再送・再計算しない |
| 起点を変えようとする | 起点に従属する未保存編集があれば破棄確認。取消時は元の起点・タブ・編集を維持。確定時は旧起点の結果・未保存編集・会話を消去する |
| 独立した入力レコード・保存済み要求を開いている | 起点変更だけでレコードの対象を変更・要求を削除しない。未保存のレコード編集は破棄確認の対象。続けて表示する保存済み要求は対象を明記する |
| 認証を切り替える | 旧利用者の取得情報・入力を破棄する。承認者は控えた要求IDから再取得する。秘密情報をブラウザ保存しない |
| 更新を実行した後、調査や比較へ戻る | 取得済みの結果を更新前と表示し、再取得を案内する。再取得前の損害額を最新値として見せない |
| 読取中に他タブへ移る | 送信元タブ・対象・世代に結果を保存し、強制移動しない。対象・認証変更後の旧応答は反映しない |

右欄の比較ボタンは、追加の決定に従い**「{起点設備コード}への対応案を比べる」**というタブ2への深いリンクへ整理する。M-204・M-208は表示例であり固定値にしない。起点・候補・選択済み入力を引き継ぎ、比較結果を自動確定しない。候補ノードM-208を選んでも、比較の起点をM-208へ変えない。

### 11.5 承認の入口と現行契約

現行v1は要求IDを人が別の承認者へ渡し、GET /update-requests/{id}から保存内容を確認する仕様。access-control §10で承認待ち一覧APIを追加しないと明記され、現行HTTPにも一覧経路はない。Claudeの「既存APIがあるか未確認」は、この照合で確認済みに更新する。

今回の改修案では要求IDの入口を採用する。承認待ち一覧・通知・そのための新APIは追加しない。一覧が必要なら、別の要望・権限・契約の変更として判断する。

### 11.6 期間の入力元がない・合わない場合

| 選択状態 | 画面表示と操作 |
|---|---|
| 経済入力あり、他の計画・能力も同一期間 | 経済入力の期間を共通期間として表示。比較へ進める |
| 経済入力なし、能力・保全計画の期間が一致 | その期間を表示。経済入力が未選択の評価範囲を明示する |
| 計画・能力・経済の期間が不一致 | 各入力の期間を並べ、不一致を表示。入力の選び直し・登録訂正へ進める |
| 安全入力が期間を覆わない | 不足する適用期間を表示し、入力を選び直せるようにする |
| 履歴・安全入力しかなく、基準となる期間がない | 共通期間を自動設定しない。期間を定める入力の選択か登録・訂正へ案内する |

過去履歴の期間を将来比較の期間へ流用しない。比較UIを読み取り専用にすることで既存APIの期間検証を弱めない。DatePickerは入力登録・訂正で使用し、未編集時の秒以下とtimezoneを保持する。

### 11.8 全タブ共通の事前選択・引継ぎ規則

- 対象設備・製品・期間・単位の条件に合う候補が1件で、該当検索に続きがないと確認できた場合だけ事前選択する。該当しない条件の欄へ無理に製品等を適用しない。
- 条件がまだ定まらない、検索の続きが未取得、候補0件・複数件なら1件と確定しない。確認中・候補なし・選択が必要な状態を区別する。
- 主画面で自動選択・手動選択した入力を、同じ起点・候補の比較タブの初期選択へ引き継ぐ。入力ID・版・条件を確認し、自動選択したことを明示して選び直せるようにする。
- 利用者が選び直した値や明示的に未選択にした値を、後から来た候補取得応答やタブ移動で上書きしない。候補の条件が変わって選択が無効になったら、理由を示して再選択を求める。
- 安全入力の事前選択と、安全条件が充足・運転許可済みという判定は別。選ばれた入力のサーバ判定・適用条件・出典を表示し、自動で安全を充足扱いにしない。主画面に安全入力を自動取得する機能は今回追加しない。
- 比較期間の導出は§4.2と§11.6のまま。1件を選ぶためだけに期間・単位を推測したり、単位換算・期間の丸めをしない。

### 11.9 参照ドロワーの構成案

目的は、タブを切り替えたため同時に見られなくなる図・結果・根拠の参照。全画面を常時2列にせず、必要時だけ取得済み情報を横に開く。

- 内容は「関係図」と「いま見ている結果の根拠」。要約帯や各結果の「関係図を見る」「根拠を見る」から開き、対象結果・起点・取得時点を表示する。閉じても選択・表示位置を保つ。
- 1280px以上は右側に固定できる。768〜1279pxと768px未満は全面の重ね表示とする。広い画面でも初期状態から常時2列にはしない。
- 開閉でAPIの再取得・名称取得・比較の再実行をしない。取得済みの結果、名称、選択ノード、図のノード位置・拡大移動を共通の状態として保持し、タブとドロワーで共有する。参照先が未取得なら未取得を表示する。
- 重ね表示はキーボードで開閉でき、閉じたら起動元へフォーカスを戻す。背面の誤操作を防ぐ。幅をまたいでも入力や結果を失わないことを確認する。
- 承認画面では、変更要求の対象と調査起点が違う場合、その図を要求の根拠として表示しない。違いと「この要求対象の関係図は未取得」を明示する。同じ設備でも取得時点・要求との関係を示し、最新の調査図を承認済みSnapshotの一部とは表示しない。新APIや影響の推測で穴埋めしない。
- 不足入力から登録・訂正へ移る場合は、カテゴリ・対象・戻り先・比較の選択を保持する。変更準備を作っただけでは業務値は変わらず、要約帯を更新済みの金額にしない。確定実行後は旧結果を更新前とし、通常の明示的な再取得で更新する。

### 11.10 ドロワーの実現性・追加工数とA全体の見積もり

#### コード照合

GraphCanvasは取得済みのGraphView・Envelope・選択・名称状態をpropsで描画し、EvidencePanelもEnvelopeから描画する。描画部品自身は再取得を必要としない。親画面には調査・比較・文書の取得済みEnvelopeが存在する。したがって**新API・業務契約変更なしで、取得済み結果を再表示する構成は可能**。

現状は調査hookが子画面内、図のノード位置がGraphCanvas内、viewportはReact Flow内にあるため、タブやドロワーのマウントで失われない共通状態への引上げ・受渡しは必要。API再取得で補う設計にはしない。実装前のコード照合であり、ドロワー自体はまだ試作・実装・実ブラウザ検証していない。
