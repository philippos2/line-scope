## 3. 上部タブの構成

```text
LineScope 設備調査                         接続設定

[接続及び影響範囲] [質問する] [対応案を比べる]
[出典と経路] [入力を登録・訂正] [変更・承認・実行]

選択中の設備：名称 · コード ／ 必要なら対象を選ぶ操作

選択したタブの内容
```

- 上記6タブは同じ階層に置く。図中の2行は狭い場合の折返し例であり、主機能・補助機能の階層分けではない。
- 初期表示は「接続及び影響範囲」。設備検索、関係図、登録状態、損害額、代替提案の調査の流れを維持する。
- 他のタブへ移っても調査の選択・取得結果を失わず、戻れば確認できるようにする。隠れている図の結果を消去することと、別設備へ切り替えた際の破棄を混同しない。
- 各タブに現在の対象設備を明示する。比較・登録・変更対象の切替は明示操作とし、タブを開いただけで登録・承認・実行しない。
- 対象未選択では、その画面から実行できる対象選択の操作を示す。「左から選んでください」だけで行き止まりにしない。
- 関係図の見出し・案内・画面説明は「接続及び影響範囲」に統一する。過去の履歴文言は書き換えない。
- 狭い画面でもタブへ到達でき、キーボードで選択・内容への移動ができることを確認する。

## 4. コード照合と修正方針

### 4.1 比較と関連文書の対象設備

`frontend/src/app/App.tsx`は、調査設備変更時に`decisionEquipment`をnullへ戻す。比較対象が設定されるのは、右欄の「この設備で対応案を比べる」等の明示操作時。下部タブを直接開くだけでは設定されない。

`RegisteredComparison.tsx`の候補取得ボタンは比較対象未設定で無効になる。関連文書検索も`decisionEquipment`を条件にしている。このため設備を検索・選択しただけでは両方が無効のままになる。

対応案は、調査中の設備を対象にする明示操作を各該当タブから利用できるようにすること。文書検索は文書検索の対象を表示し、比較という別機能の操作を先に要求しない。対象未選択・処理中・権限不足・検索先の接続不良を区別する。

### 4.2 共通比較期間の日時選択

`frontend/src/features/decision/RegisteredComparison.tsx`の開始・終了はtype指定のないinputで、現在はtimezone付き文字列をそのまま編集・送信している。

- 日付と時刻を選択する入力にする。ブラウザ標準の日時選択か既存構成に合うDatePickerかは、実装時に対応ブラウザと操作性を確認して選ぶ。現時点で新規ライブラリを確定しない。
- 表示の基準を日本時間と明示する。APIへはtimezone付きの日時を送る。UTC値をローカル文字列に切り詰めるだけの変換はしない。
- 開始・終了、入力値の妥当性、開始より終了が後であることを検証する。
- 経済入力の適用期間からの初期設定を維持する。能力・計画の一致期間、安全入力の対象期間を覆う条件等、既存の比較契約は変更しない。
- 主画面の損害額の読み取り専用期間と、比較タブで選択する共通比較期間は別のUI。日時選択を加えることで主画面の算定条件を自由に変更できるとは扱わない。

### 4.3 入力登録・訂正の候補

対象は4カテゴリの検索・作成・訂正にある入力欄。現状の各Panelとその編集部品を棚卸しして、フィールドごとに候補取得元・入力方式・検証規則を対応づけてから実装する。

| 欄の種類 | 設計方針 |
|---|---|
| 名称・コード・出典等の文字列 | 既存の登録内容等に由来する候補を選べ、候補外の値も手入力できる。候補の根拠と取得範囲を定める |
| 設備・製品等への参照 | 人が名称・コードから選べるようにする。自由入力は検索語として扱い、存在しないIDを推測・生成しない |
| 数量・金額・単位 | 手入力と候補選択の両立を検討する。値を架空の既定値で埋めず、型・単位・未知の扱いを維持する |
| 日時・期間 | 日時選択と手入力の扱いを整理し、timezone付きAPI契約を維持する |
| 真偽値・種別など契約で値が限定される欄 | 許可値の選択と入力補助を提供する。候補外の任意値を受理するよう業務契約を変更しない |

§9の調査で、登録済み値を候補にするための既存検索・詳細APIは確認した。専用の候補辞書・自動採番APIは今回確認しておらず、その追加を前提にしない。足りない場合は必要な変更を報告してから判断する。M-204/M-208や固定金額の専用候補を埋め込まない。未選択・不明・0は区別し、候補の選択だけで変更を確定しない。

### 4.4 変更・承認・実行

現状には次の無効条件がある。§9で初期状態と有効化経路を実画面で確認したが、開発依頼者が操作した全状態を再現したわけではない。

| 操作 | 現在の無効条件の例 |
|---|---|
| 登録状態の変更下書き | 変更後の状態が未選択 |
| 変更準備を作成 | 指示本文が空、または処理中 |
| 保存状態を再取得 | 要求IDがUUID形式でない、または処理中 |
| 承認・拒否 | 保存内容の確認未チェック、有効性条件未充足、承認待ちでない、処理中 |
| 実行 | 保存内容の確認未チェック、有効性条件未充足、承認済みでない、処理中 |

実装着手後、実画面の操作・返却状態・権限を照合して原因を特定する。無効条件は理由と次に必要な操作を示す。Prepare→別担当者のApproval→元依頼者のExecute、期限・version・Snapshot・再送キー等の制約を外して有効化しない。

### 4.5 質問機能

LLM接続の復旧と今回のUI改修を分ける。5174番は既存Ollama/Qwenへ接続を復旧し、実質問がHTTP200/status okで回答することを確認済み。残るのは選択設備の引継ぎと原因別エラー表示。

「この設備」の質問対象を画面で明示し、設備を切り替えた後に旧設備の会話が新設備へ混ざらないことを確認する。既存の設備・権限・確定操作の契約を変更しない。

## 6. 確認項目

- 6タブが上方の同じ階層にあり、改称が反映される。390／768／1600pxとキーボードで操作できる。
- 設備未選択・選択済み・設備切替の各状態で、対象の案内とボタン状態が一致する。

## 9. 深掘り調査の結果と限界

### 9.1 実画面の変更操作

5174番に工場管理者として接続し、既存ブラウザ検証イメージを再利用した。新規イメージは作っていない。変更要求作成・承認・拒否・実行のリクエストは送信しないよう遮断した上で、表示とローカル入力を確認した。遮断に該当する送信自体も発生していない。

| 操作状態 | 実画面の結果 | 判定 |
|---|---|---|
| 設備未選択で変更タブを開く | 「変更準備を作成」「保存状態を再取得」は無効。状態変更の欄はない | 対象・本文・要求IDがない初期状態 |
| M-204を選び変更タブへ移る | 「変更の下書きを作る」も無効、指示本文は空 | 変更後状態の選択が必要だが、次の操作の案内が不十分 |
| 変更後状態を稼働中にする | 下書きボタンだけが有効になる | 状態選択から下書きへは接続している |
| 下書きボタンを押す | 指示本文が入り「変更準備を作成」が有効になる | 準備ボタンが常に壊れているわけではない。下書き→サーバへの準備依頼という2段階が分かりにくい |
| 指示本文を消す | 準備ボタンは再び無効 | 本文の有無という実装条件と一致 |
| UUID形式の要求IDを入力 | 「保存状態を再取得」が有効になる | 形式チェックは機能。実在しない調査用IDで読取は実行していない |

この範囲でDB・承認基盤の故障を示す証拠は得られなかった。一方、準備要求の作成、保存Snapshotの取得、別担当者の承認、元依頼者の実行は今回実施していない。既存のActionPanelテストには確認チェック、期限切れ、競合、拒否、通信断の検査があるが、読んだだけであり、今回の実環境での成功証拠にはしない。

修正の中心は対象・変更内容・下書き・準備済み要求の段階を明示すること。初期状態や無効ボタンの近くに「変更後の状態を選んでください」「下書きから変更準備を作成してください」「要求IDを入力してください」等、現在不足する条件を表示する。承認・実行は保存済み要求の状態と操作主体を表示し、正当な制約を外さない。

### 9.2 入力候補の取得経路

コードに加え、5174番の実APIへ読み取り専用の検索・詳細要求を送った。検索はPOSTだが業務値の変更を行わない。

| 用途 | 既存経路 | 実応答 | 設計上の使い方 |
|---|---|---|---|
| 費用・経済の既存入力 | POST /economic-inputs/search → GET /economic-inputs/{id} | HTTP200、1件。詳細に期間・稼働時間・費用項目・製品別損害額 | 出典・値・期間を含む既存登録から候補を構成できる |
| 生産能力の既存入力 | POST /capacity-inputs/search → GET /capacity-inputs/{id} | HTTP200、1件。詳細に単位・必要／通常／使用中／予約能力・出典等 | 同じ欄・単位・製品の登録値を参考候補にできる |
| 安全入力 | POST /safety-inputs/search、GET /safety-inputs/{id} | 検索HTTP200、0件。GETの処理・スキーマはコード確認のみ | 現環境には候補元がない。架空の安全基準・条件を提示せず、候補なしでも手入力できるようにする |
| 対応計画・故障履歴 | POST /maintenance-inputs/search、GET /maintenance-inputs/{id} | 検索HTTP200、0件。GETはコード確認のみ | 同上。内容の候補表示は未検証 |
| 製品参照 | POST /capacity-inputs/products/search | HTTP200、3件。名称・コード・IDが返る | 自由入力の検索語から候補を選ぶ。既に能力編集画面で使用されている |
| 次回保全の関連付け | GET /maintenance-inputs/next-plans/{equipment_id} | HTTP200、complete=true、候補0件 | 既存の候補選択を再利用する。将来の予定だけを対象とする既存契約を維持 |
| 設備参照 | 関係分析のsearch_equipment直接経路 | 実画面の検索でM-204を選択できた | 他タブでも共通の対象選択導線に利用できる |

検索一覧にはpayloadがないため、出典・数値の候補化には詳細GETが必要。最初から全件・全詳細を一斉に取得せず、対象とカテゴリを絞り、ページ・同時要求・取得件数を制限する。取得済み範囲を超えて「候補なし」と断定しない。

### 9.3 欄ごとの制約

- 既存登録の値は参考候補であり、推奨値・適用可能な安全条件とは限らない。候補には対象・出典・適用期間等を示し、利用者が明示選択する。安全条件や費用を自動で充足済みにしない。
- 入力コードは作成時の識別子。既存コードを候補としてそのまま新規登録すると重複し得る。訂正では既存の設備・入力コード等は変更不可で、payloadのみを変更する契約がある。候補対応のためにこれを解除しない。
- 種別・判定・確度・真偽値は既に選択UIがある。自由入力を加えるために許可値を拡張しない。
- 製品・保全予定は既存参照から選択し、未知のIDを生成しない。数値は手入力可能とし、候補なしを0にしない。日時は日時選択の設計を共通化する。
- 新規採番の自動化、全社的な候補辞書、未登録の安全・保全情報の追加は本調査で実現していない。必要だと判断した場合は範囲を別途確認する。

### 9.4 工数評価と調査終了

現在の証拠では、既存の契約を維持したFrontendの導線・候補表示の改修が中心であり、DB・承認処理の作り直しや候補専用APIを必須とする根拠はない。基本2 PR・4〜6作業日の計画は据え置く。ただし承認・実行の実環境受入と、候補0件のカテゴリの実データ表示は未確認であり、追加変更が不要と保証しない。

開発依頼者の「一定範囲を調べても評価不能なら一旦止める」指示に従い、この範囲で調査を終了した。未確認を埋めるための試験用データ投入・変更要求作成・権限変更は行っていない。実装開始命令までは修正しない。
