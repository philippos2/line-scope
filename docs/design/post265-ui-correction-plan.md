## 3. 上部タブの構成

```text
LineScope 設備調査                         接続設定

[接続及び影響範囲] [質問する] [対応案を比べる]
[出典と経路] [入力を登録・訂正] [変更・承認・実行]

選択中の設備：名称 · コード ／ 必要なら対象を選ぶ操作

選択したタブの内容
```

- 上記6タブは同じ階層に置く。図中の2行は狭い場合の折返し例であり、主機能・補助機能の階層分けではない。
- 初期表示は「接続及び影響範囲」。設備検索、関係図、登録状態、損害額、代替提案の調査の流れを維持する。
- 他のタブへ移っても調査の選択・取得結果を失わず、戻れば確認できるようにする。隠れている図の結果を消去することと、別設備へ切り替えた際の破棄を混同しない。
- 各タブに現在の対象設備を明示する。比較・登録・変更対象の切替は明示操作とし、タブを開いただけで登録・承認・実行しない。
- 対象未選択では、その画面から実行できる対象選択の操作を示す。「左から選んでください」だけで行き止まりにしない。
- 関係図の見出し・案内・画面説明は「接続及び影響範囲」に統一する。過去の履歴文言は書き換えない。
- 狭い画面でもタブへ到達でき、キーボードで選択・内容への移動ができることを確認する。

## 4. コード照合と修正方針

### 4.1 比較と関連文書の対象設備

`frontend/src/app/App.tsx`は、調査設備変更時に`decisionEquipment`をnullへ戻す。比較対象が設定されるのは、右欄の「この設備で対応案を比べる」等の明示操作時。下部タブを直接開くだけでは設定されない。

`RegisteredComparison.tsx`の候補取得ボタンは比較対象未設定で無効になる。関連文書検索も`decisionEquipment`を条件にしている。このため設備を検索・選択しただけでは両方が無効のままになる。

対応案は、調査中の設備を対象にする明示操作を各該当タブから利用できるようにすること。文書検索は文書検索の対象を表示し、比較という別機能の操作を先に要求しない。対象未選択・処理中・権限不足・検索先の接続不良を区別する。

### 4.2 共通比較期間の日時選択

`frontend/src/features/decision/RegisteredComparison.tsx`の開始・終了はtype指定のないinputで、現在はtimezone付き文字列をそのまま編集・送信している。

- 日付と時刻を選択する入力にする。ブラウザ標準の日時選択か既存構成に合うDatePickerかは、実装時に対応ブラウザと操作性を確認して選ぶ。現時点で新規ライブラリを確定しない。
- 表示の基準を日本時間と明示する。APIへはtimezone付きの日時を送る。UTC値をローカル文字列に切り詰めるだけの変換はしない。
- 開始・終了、入力値の妥当性、開始より終了が後であることを検証する。
- 経済入力の適用期間からの初期設定を維持する。能力・計画の一致期間、安全入力の対象期間を覆う条件等、既存の比較契約は変更しない。
- 主画面の損害額の読み取り専用期間と、比較タブで選択する共通比較期間は別のUI。日時選択を加えることで主画面の算定条件を自由に変更できるとは扱わない。

### 4.3 入力登録・訂正の候補

対象は4カテゴリの検索・作成・訂正にある入力欄。現状の各Panelとその編集部品を棚卸しして、フィールドごとに候補取得元・入力方式・検証規則を対応づけてから実装する。

| 欄の種類 | 設計方針 |
|---|---|
| 名称・コード・出典等の文字列 | 既存の登録内容等に由来する候補を選べ、候補外の値も手入力できる。候補の根拠と取得範囲を定める |
| 設備・製品等への参照 | 人が名称・コードから選べるようにする。自由入力は検索語として扱い、存在しないIDを推測・生成しない |
| 数量・金額・単位 | 手入力と候補選択の両立を検討する。値を架空の既定値で埋めず、型・単位・未知の扱いを維持する |
| 日時・期間 | 日時選択と手入力の扱いを整理し、timezone付きAPI契約を維持する |
| 真偽値・種別など契約で値が限定される欄 | 許可値の選択と入力補助を提供する。候補外の任意値を受理するよう業務契約を変更しない |

候補の取得元が既存APIで足りるかは未確認。足りない場合は必要な変更を報告してから判断する。M-204/M-208や固定金額の専用候補を埋め込まない。未選択・不明・0は区別し、候補の選択だけで変更を確定しない。

### 4.4 変更・承認・実行

現状には次の無効条件がある。これは原因の候補であり、今回報告されたボタン無効の原因確定ではない。

| 操作 | 現在の無効条件の例 |
|---|---|
| 登録状態の変更下書き | 変更後の状態が未選択 |
| 変更準備を作成 | 指示本文が空、または処理中 |
| 保存状態を再取得 | 要求IDがUUID形式でない、または処理中 |
| 承認・拒否 | 保存内容の確認未チェック、有効性条件未充足、承認待ちでない、処理中 |
| 実行 | 保存内容の確認未チェック、有効性条件未充足、承認済みでない、処理中 |

実装着手後、実画面の操作・返却状態・権限を照合して原因を特定する。無効条件は理由と次に必要な操作を示す。Prepare→別担当者のApproval→元依頼者のExecute、期限・version・Snapshot・再送キー等の制約を外して有効化しない。

### 4.5 質問機能

LLM接続の復旧と今回のUI改修を分ける。5174番は既存Ollama/Qwenへ接続を復旧し、実質問がHTTP200/status okで回答することを確認済み。残るのは選択設備の引継ぎと原因別エラー表示。

「この設備」の質問対象を画面で明示し、設備を切り替えた後に旧設備の会話が新設備へ混ざらないことを確認する。既存の設備・権限・確定操作の契約を変更しない。

## 5. 実装に進む場合の作業順

1. 本書のレビュー。入力候補の取得元と、変更・承認・実行の無効条件の未調査部分を明示する。
2. 実装開始の明示命令を受ける。
3. 対象設備の受渡しと上部タブを整え、比較・文書検索・入力・変更操作へ到達できるようにする。
4. 日時選択・候補付き入力・原因別案内を実装する。既存APIで実現できない範囲は勝手に拡張しない。
5. 5174番で実画面を確認し、開発依頼者が最新版を試せる状態になったら報告する。5173番は変更しない。

PR本数は未確定。候補取得元と変更操作の原因調査を終えてから、利用可能な導線を単位に見積もる。文書化の依頼を実装・新規PR作成の承認へ読み替えない。

## 6. 確認項目

- 6タブが上方の同じ階層にあり、改称が反映される。390／768／1600pxとキーボードで操作できる。
- 設備未選択・選択済み・設備切替の各状態で、対象の案内とボタン状態が一致する。
- 比較タブ内から対象を指定し、候補取得→入力選択→日時選択→比較結果へ進める。
- 日本時間の選択とAPIのtimezone付き日時が往復で一致する。登録期間が合わない場合は理由が分かる。
- 比較対象を設定する前でも、文書検索の対象指定から検索を実行できる。出典・経路は表示を主とし、編集は入力登録へ分ける。
- 各入力欄で、手入力と候補選択、候補なし・検索失敗・不正値を確認する。候補外の値の扱いは欄の契約に従う。
- 変更準備→別担当者の承認→元依頼者の実行を実画面で確認する。無効時の理由と次の操作が分かる。
- 質問対象の設備が明確で、切替・遅延応答・接続解除で旧結果が復元されない。LLM障害等の案内が原因に合う。
- 文書作成時点では上記の改修・受入を実施していない。追加試験は実装前に件数と範囲を見積もる。
