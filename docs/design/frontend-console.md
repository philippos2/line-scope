# Frontend オペレーション画面の設計

要件の正本は[requirements §13](../requirements/requirements.md#13-後続frontendフェーズ)、業務目的は[Use Case](../requirements/use-cases.md)、権限は[access-control](../requirements/access-control.md)、APIは[api-tools](../implementation-design/api-tools.md)。本書は現バックエンドへ接続する画面・実装計画であり、新しい業務データや規則を定義しない。

> [シナリオ1のUI再設計案](frontend-redesign-proposal.md)はレビュー待ちの別文書です。以下は現行設計の記録であり、再設計案の承認・実装済みを意味しません。

## 最初に通す体験

M-204の異常をエンドユーザーが認識し、問い合わせる → 現在状態と影響候補を確認 → 仮置き条件による対応案比較 → Evidenceと不足情報を確認 → 必要なら明示Prepare → 別の承認者がSnapshotを確認してApproval → 元requesterがExecute → 更新後を確認する。

自動異常検知・Incident一覧・工場全体の損失集計は追加しない。初回は既存の分析経路と実際の更新を画面で利用可能にする。架空のSeverity、Location、工場全体KPIを表示しない。

## 上部タブへの移行時の設備検索

設備検索と候補一覧は左ペインに常時表示し、6タブで共有する。6タブは画面全幅ではなく、左ペイン右側のメイン領域の最上部に配置する。設備を選択しても一覧を閉じず、起点の候補を文字と選択状態で識別する。要約帯の起点変更は左ペインの検索欄へフォーカスする。検索の共通化を理由に左ペインを廃止しない。狭い画面では検索をタブ内容の上に縦積みし、検索結果を保持する。

## 情報構造と利用者の問い

UIの中心は、業務上の意味を持つノード間の関係と、起点から及ぶ影響範囲の理解である。個別設備の状態や機能の操作順だけを主画面にしない。利用者の問いは「何とつながるか」「止まるとどこまで影響するか」「どの経路が根拠か」「何に依存し、代替や共通の弱点があるか」とする。

初期画面には「登録設備を表示して調査を始める」を置き、実検索の候補を中央へ表示する。設備を選ぶと既存のサーバ分析経路で下流影響と上流依存を取得し、関係Graphを開く。名前・コードによる検索も左側から行える。

左は検索と対象設備、中央は大きな関係Graph、隣は選択ノードの取得済み属性と代表経路。Graphの下に調査回答・比較・根拠・入力管理・変更承認の文脈パネルを置く。パネルを切り替えてもGraphと選択対象を消さない。狭い画面では検索、Graph、詳細を縦に配置する。

Graphの種別色は設備・工程・生産作業・製品・インフラを区別し、直接／間接影響候補はサーバ分類を文字でも表示する。ノード選択で当該ノードを含むサーバ返却の代表経路だけを強調する。上流探索を下流停止影響と呼ばず、非CURRENTの結果は正常Graphとして表示しない。工場全体の一覧を取得したかのように表示しない。

React Flowを表示・選択・移動・拡大縮小・全体表示・ミニマップに使用する。UI上のdragや選択は業務データを変更しない。依存探索・代替成立・SPOF判定はサーバに維持し、描画の都合で関係・影響を生成しない。任意のedge作成・削除・再接続は公開しない。

段階1はGraph中心の基本調査と既存業務機能の保持。段階2で複数ノードの共通依存・代替・SPOFの調査操作を整える。段階3で比較・根拠・変更対象とGraphの連動を仕上げる。段階1の成功だけで全UIや全BSの受入を宣言しない。

接続解除・切替で取得情報を消去し、対象設備変更で以前の編集・比較を破棄する。比較Envelopeを根拠表示へ引き継ぐ。変更確定後の取得済み結果は再取得前と表示する。認可・承認・実行の契約は維持する。

## APIと表示の対応

| 操作・表示 | 既存API / 結果 | UIの責務 |
|---|---|---|
| 問い合わせ | POST /agent、message / context_id / as_of | contextと要求を区別。通常調査・明示Prepareを区別して送る |
| 状態と判断材料 | data.decision_package.equipment / impact / comparison / maintenance / summary | 現在状態と正式入力の共通期間評価を分ける。未選択・nullを0へ変換しない |
| 通常Graph調査 | data.tool_resultsのGraph結果とevidence.tool_results | 経路・分類・complete・limit_reason・分析時刻を同じ結果から表示 |
| Evidence | evidence、計算式・入力・引用・保全根拠 | 対応する結論から詳細へ移動。見つからない情報を補完しない |
| Prepare結果 | POST /agentのdata.update_request_id等 | 明示クリック時だけ送信し、before / proposedを表示 |
| 保存要求の確認 | GET /update-requests/{id} | サーバ保存Snapshotとhashを確認し、古い分析から再生成しない |
| 承認・拒否 | POST /approvals/{id}/approve、/reject | approveは保存snapshot_hashを送る。エンドユーザーが操作する |
| 実行 | POST /update-requests/{id}/execute | 元requesterの明示操作。確定afterとcurrent_snapshotを分ける |
| 接続確認 | GET /health /health/ready | readinessはPGの確認。Graph・RAG・モデル全体のReadyにしない |

UIにToolsを個別HTTP公開するためのAPIを追加しない。Graph・モデル・RAGの未観測状態は未確認と表示する。役割を自己申告して権限を決めない。初回はBearer token入力で/session/loginへ接続し、再読み込み時は/sessionでセッションとidentityを確認する。role / user_idを画面で推測しない。操作可否の最終判定はサーバの認可に従う。

## 更新操作とセキュリティ

Bearer tokenは初回接続時だけ送信し、サーバ側のセッションに保持する。ブラウザではHttpOnlyのopaque cookieで接続を復元し、localStorage、sessionStorage、URL、ログへtokenを保存しない。上部の接続設定で接続切替・解除を行い、解除はサーバセッションと取得済み結果・context・変更要求を消去する。F5で認証状態を復元するが、分析結果の永続復元は行わない。開発用Frontend proxyから同一originのAPIへ接続し、BackendのCORSを広げない。

分析・Prepare・Approval・Executeを別操作にする。分析でデータを変更せず、Agent応答から自動approve / executeしない。承認対象はサーバSnapshotであり、LLM回答ではない。承認者へ切り替えるときは接続解除して別tokenで対象要求を読み直す。requesterへ戻すときもサーバ状態を読み直す。

更新要求IDとretry keyを区別する。Prepareは同じ操作の再送で同じIdempotency-Keyを使い、内容変更時は新しいキーを使う。成否不明時に書込を無条件で自動再試行しない。Approve / Execute後は保存要求を読み直し、サーバ確定結果で表示を更新する。30分期限はサーバが判定し、画面時計を権限根拠にしない。

LLM / 文書 / Toolの文字列はtextとして表示する。HTML実行・任意URLへのtoken転送・内部推論の表示を行わない。新しい調査の送信中は前の結果を未確認の最新状態として示さず、古い結果と明示する。遅れて返った過去の応答が新しい結果を上書きしないよう要求を識別する。

## 実装の構造

React / TypeScript / Viteを使用し、依存versionはlockfile、Node imageはDockerfileのdigestで固定する。Graph描画ライブラリは実際の経路を描いた操作性で選ぶ。最初からReduxや汎用Plugin基盤を入れない。

```text
frontend/src/
  app/          接続状態・画面組立
  api/          HTTP、Envelope、公開エラー、要求の再送制御
  features/
    investigation/ 問い合わせ・結果の連動
    graph/         サーバ経路の表示変換と描画
    decision/      比較とunknown表示
    evidence/      根拠の詳細
    actions/       Prepare / Approval / Execute
  components/   共通表示部品
```

対応Unit Testは同じ責務の近くに置き、業務E2Eは別にする。表示変換に依存関係探索・費用計算・認可を実装しない。

## 到達点と検証資料

現行画面はReact Flowを使用する。計画工程と残項目は[ロードマップ](../roadmap.md)、検証手順は[Frontend README](../../frontend/README.md)、旧画面の到達点・初期計画は[文書整理の履歴](../history/2026-10-18-documentation-organization.md)を参照する。

## 設備コードを暗記しない対象選択

取得した設備候補からエンドユーザーが対象を選ぶと、そのequipment_idで読み取り専用の下流・上流調査を行う。選択だけでPrepareしない。対象を選び直すと前のconversation contextを引き継がず、サーバで存在・認可を再検証する。

取得候補を工場全体の一覧とは扱わず、続きが未取得の場合は絞込みを案内する。Graphの選択設備を比較・入力へ引き継ぐ操作は明示ボタンで行い、調査起点とは区別する。新しいTool公開HTTP APIや架空のライン・場所・稼働状態は追加しない。

## 正式経済入力の業務経路

「正式な経済・損失入力」で登録済み入力を設備名・コード・入力コードから検索し、候補を明示選択する。取得時の比較期間・稼働時間・version・出典、案別見積総額／既知小計と未知・非独立・非網羅を表示し、UIで再計算・最安順位付け・安全判定をしない。統合比較は利用者が正式入力と共通期間を明示選択する。

新規登録は既存の設備検索候補で設備を選択した後にフォームを開く。訂正は取得済み入力を読み込んでpayload全体を編集し、ID・設備・入力コードを変更しない。金額／時間の空欄はnull、明示0は文字列0として保持。項目の適用期間の空欄は、フォームで明示した共通比較期間を使うことを表示し、保存Snapshotで確認する。網羅性・独立性のチェックを自動で肯定しない。Prepare後は要求IDを既存Action画面へ渡し、別managerが保存Snapshotを承認、元requesterがExecuteする。

登録値は取得時の結果であり、確定操作後は再取得を促す。選択記録をAgentへ問い合わせるボタンはID付き質問の下書きだけを作り、送信は明示操作。接続解除・接続切替時に検索結果・編集状態・再送キーを破棄し、AbortSignalと応答確認で遅延応答の復元を防ぐ。新しい編集を開くと未保存値をリセットする。

## 正式能力入力の業務経路

能力入力パネルは設備候補と製品名／code検索から登録対象を選び、同一製品・数量単位・期間の必要能力・通常能力・使用中／予約負荷を明示入力する。互換性は不明を初期値とし、負荷の重複なし・網羅性・復旧条件を自動肯定しない。数量の空欄はnull、0は文字列の0として保持する。

明示Prepareの保存要求を共通Actionへ渡し、別manager承認・requester確定を分離する。同じ内容の再送は同じretry key、内容変更時は新しいkeyを使う。計算表示はサーバ値を使い、能力充足を完全代替・安全と表現しない。登録値の検索・訂正フォーム読込・再取得と、選択IDを含むAgent質問の下書きを提供する。Agent送信は別の明示操作。確定後の結果は再取得を促し、接続解除で画面を破棄・遅延応答を無視する。出典はtextとして表示する。

## 正式安全入力の業務経路

- 設備候補を選択し、安全入力の出典・観測・基準・適用期間・継続条件をフォームへ登録する。判断の初期値はUNKNOWN、確度はESTIMATED。
- 明示Prepareの保存要求を共通Actionで確認し、別manager承認・requester確定を分離する。
- 検索から選択した登録値の停止必須・条件付き・不明、継続候補の除外理由、出典と条件を表示する。判定はサーバで行う。
- 訂正、同一内容のretry key保持、確定後の再取得、閉じる／接続解除時のabortを適用する。出典をHTML実行しない。
- Agent質問は選択IDを含む下書きとし、送信は別の明示操作。運転許可や設備全体の安全と表現しない。

## 対応計画・故障履歴

選択設備から正式入力を登録し、分類・期間・出典・調達待ち・作業・停止・費用・交換費算入を明示する。将来PLANNEDの次回候補を取得し、同時刻は利用者が選んで関連付ける。予定本体の作成・承認は既存保全経路を使う。Prepareから共通Actionへ渡し、別manager承認・要求者確定の後に再検索・再取得する。取得時結果と確定後currentを区別し、Agentへの問い合わせは明示送信する。履歴の入力では過去事象期間と過去停止損失を扱い、未知を0や将来予測にしない。接続解除・編集終了時に送信をabortし、storageへ保存しない。

## 正式入力の統合比較画面

選択設備から経済・能力・安全・対応計画の候補を取得し、出典・期間・versionを確認して選択する。経済は一つ、その他は明示した候補を選ぶ。経済入力の詳細参照で評価期間を記入し、必要なら利用者が変更する。期間・対象の不一致はサーバで拒否する。入力がない場合も空の選択で不明を確認できる。

比較結果は既存の対応案カードで表示し、調達待ち・作業・停止時間、経済小計／総額と計画直接費小計、製品の能力単位、条件付き復旧期限を分ける。選択と期間をAgentへの問い合わせに使う場合も、利用者が別途送信する。接続解除・設備切替で結果と選択を消去し、確定操作後は取得済み比較を古い結果と表示する。

正式入力の比較画面とAgent比較結果は、上流依存インフラを下流影響と別の欄に表示する。サーバのtyped ID・complete / limit_reason・経路を使用し、資源状態・供給能力・停止被害をUIで生成しない。Evidence欄からGraph世代・観測時刻を確認できる。

比較は、代替の構造・能力・登録上の安全判断・品質未確認を別々に表示する。共通期間の登録費用差と未算出案、選択した過去履歴、六次元の事実／不足を根拠欄へ接続する。過去損失を将来費用へ加算せず、低費用を実行推奨へ変換しない。

経済入力では任意の単純費用回収条件を登録・訂正できる。条件の有無、日次稼働、三値の仮定、出典・確度を明示し、保存済みSnapshotから承認・確定する。経済入力結果と統合比較にサーバ算出の日数・式・仮定・不足を表示し、Frontendでは再計算しない。

## 複数対象のGraph調査

Graphの選択ノードを「重要対象」「除外対象」「SPOF候補」にそれぞれ追加・解除する。共通依存は重要対象2件以上、代替は重要対象と除外対象各1件以上で開始する。SPOFは必須上流の自動探索か明示候補を選ぶ。明示候補なしでの実行を無効にし、省略と空配列を取り違えない。除外対象は代替分析では同時除外、SPOFでは候補を個別除外する。

選択したtyped IDをPOST /agentの「関係分析」契約へ直接送信する。分析判定はサーバの結果を表示し、ブラウザで到達・代替・SPOFを計算しない。共通依存先、重要対象ごとの除外前後、代替候補、重要対象とSPOF候補の組別判定をGraphの近くへ表示する。不明・探索不完全・未評価を保持し、空の評価を障害点なしと扱わない。


## 取得済みGraphと更新操作の区別

問い合わせ中という理由だけでは「更新後の関係が未確認」の警告を出さない。Graphの取得時点と、同一画面での更新実行試行の前後関係を区別する。更新実行試行後は、保持しているGraphが再取得前であることを示す。実行応答が不明な場合もあるため、業務データが変更済みとは断定しない。

属性取得・文書検索・通常の問い合わせは、Graphを再取得したことにしない。Graphを含む新しい応答を受けた時点で、その取得開始時の更新世代を記録する。取得中に別の更新実行があれば、応答後も更新後未確認として扱う。非CURRENTの結果を正常Graphに戻すための解除処理にはしない。

変更・承認・実行の文脈から、対象設備の関係・影響の再取得と正式入力の比較へ戻れるようにする。設備を選び直して調査条件を不用意に破棄しない。別利用者への接続切替では、これまでどおり取得情報を破棄する。他sessionの更新を自動検知する表示ではなく、Graphは取得時点の結果として扱う。


## Graph選択から比較・入力への引継ぎ

Graphの調査起点と、比較・入力の対象設備を別に保持する。ノードを選択しただけでは比較対象を変えない。Equipmentノードの登録名称・コードを取得・確認した後、「この設備を比較・入力の対象にする」で明示的に引き継ぐ。

切替後も起点のGraph・選択ノード・構造分析の重要対象等を保持する。比較候補の取得・比較API・入力フォームは明示選択された設備IDを用い、比較のEvidenceはその比較応答に対応させる。別設備へ切り替える際は以前の設備の入力選択・比較期間・比較結果・文書結果・入力編集・読込済み変更要求を消去する。変更準備・承認・実行は別途明示操作し、Graph選択だけで作成・確定しない。

調査起点と比較・入力対象を画面に表示する。製品や工程をEquipmentと推測して引き継がず、Equipmentの名称・コード未取得時は属性取得を案内する。設備検索で新しい調査起点を選ぶ場合と、保持中のGraphから比較対象だけ選ぶ場合を区別する。

## 設備調査：M-204停止とM-208代替候補

現行の操作・配置は[シナリオ1の画面設計](frontend-redesign-proposal.md)に従う。設備検索を入口にし、経済入力の有無で設備を除外しない。

- 左：設備検索。初期表示に固定設備を置かず、名称の部分一致とコードの完全一致から候補を得る。
- 中央上：選択設備の関係図。設備名とコードを併記し、登録状態を別表示する。下流影響と上流依存を切り替える。代替候補を識別する。
- 中央下：推定損害額と代替提案。金額と能力判定はサーバ値を表示し、未確認を0や充足済みとしない。
- 右：選択ノードの属性と経路。関係図の全ノードを名称・コードで識別できるよう、既存get_*の直接経路で同時4件・最大100ノードまで取得する。詳細は選択時にも確認できる。生産作業は作業コードで表示する。
- 下段：質問、対応案比較、出典と経路、入力登録・訂正、変更・承認・実行。対象の引継ぎと変更準備は明示操作とする。

デモの初期状態はM-204のみ停止、M-208は稼働中とする。設備名に異常内容を混ぜない。M-204の主軸異常はシナリオの前提であり、M-208の冷却系異常・停止を表示する旧シナリオは使用しない。

世代不一致・非CURRENTを正常な関係図として合成しない。対象切替・接続解除・遅延応答で古い結果や下書きを復元しない。更新実行後は取得済み結果を更新前と扱い、再取得を案内する。

## 代替提案の評価範囲と表示

- 主画面の比較要求は安全入力を選択していないため、安全欄は「今回の評価では安全条件の入力を選択していません」とする。未登録とは断定しない。安全入力を取得・選択する機能は今回追加しない。
- 品質・残るリスクは現行版で評価対象外。主表示の「未確認」の行を除き、「品質・残るリスクは、この版では評価対象外です」を常時表示する。返却値・詳細は技術情報で確認できる。
- 代替費用は現行比較処理が算定しない。「この版では、代替運転の費用を比較結果に含めていません」と説明し、データ登録で解消するとは案内しない。
- 継続条件の不足は安全判定に応じて説明する。停止必須なら停止が必要、条件付きならその条件に従う必要、その他は今回確認できていない旨を表示する。「確認条件を確認してください」は使わない。
- 能力入力は対象製品・版・適用期間で選ぶ。入力コードは技術情報へ置く。期間はAsia/Tokyoで「YYYY/MM/DD HH:mm〜YYYY/MM/DD HH:mm（日本時間）」と表示し、送信する期間値は変更しない。
- 比較結果に利用可能性が表示される場合、候補カードでは重複させない。運転許可の注記は評価内で1回とする。

損害額の算定データの出典は同一文字列ごとにまとめる。出典が共通なら1回だけ表示し、異なる出典がある場合は、それぞれに対応する製品の名称・コードを併記する。登録データ・金額・計算方法は変更しない。

右側メイン領域の6タブは、ページのスクロール中も上端に固定する。背景と重なり順を設定し、狭い画面ではタブ内を横スクロールできる。

文書検索結果は文書名、本文抜粋、節、版を表示し、識別子等は技術情報へ折りたたむ。文書検索の接続は環境一覧を参照する。

選択項目ペインの固定位置はメニューの実測高さに余白を加えて決める。メニューが折り返してもタイトルを隠さず、ペイン内部のスクロール時もタイトルを保持する。

## 比較タブの入力確認と結果

主画面から引き継いだ入力は、候補一覧の取得前でも同じチェック欄に表示し、変更・解除できる。対象設備・製品・版・期間を併記し、詳細操作は内容と出典を日本語で表示し、表示先へフォーカスする。比較実行後も結果へフォーカスする。未取得と候補なしを区別する。JSONと識別子は技術情報へ残す。

代替の評価は主画面と同じ表示部品を使い、利用可能性と能力のゲート、評価した製品の範囲、運転許可ではないことを維持する。修理等の算定できない項目は理由をまとめ、判明した金額と0はそのまま表示する。品質・残るリスクの評価対象外と、選択入力不足を区別する。比較の停止費用と主画面の製品別損害額は算定範囲が違うため、その違いを明示する。

比較条件を質問欄へ引き継ぐ場合、表示は対象と操作の概要にし、IDと期間は送信時の内部データで保持する。質問文を編集したら条件の引継ぎを解除して通常質問に戻す。起点変更・接続解除でも解除する。

比較の共通候補取得では、安全条件・対応計画および主画面から未引継ぎの分類を取得する。引継ぎ済みの算定・能力データは再取得せず、別候補の検索を分類ごとの操作に分ける。完了時は取得件数を表示し、0件・未取得・続きあり・失敗を区別する。候補取得だけで比較結果を消さず、選択入力・版・期間の変更時に無効化する。分類ごとの失敗で他分類の結果や選択を消さない。

## 取得済み情報の参照ドロワー（A2）

タブ下の「関係図を見る」「根拠を見る」から、タブを移動せず取得済み情報を参照する。調査・比較の根拠ボタンも対応する結果を開く。質問は回答、出典タブは表示中の種類を対象とし、未取得を他の結果で穴埋めしない。

1280px以上は右固定に必要な幅を主領域の外に確保し、狭幅は全面の重ね表示にする。Escapeで閉じて起動元へフォーカスを戻す。重ね表示中は背面を操作できない。図の方向・選択・手動位置・拡大移動と名称は主画面と共有し、開閉・参照中の選択で再取得しない。

要求を参照中は、保存内容から対象設備を特定して起点と照合する。対象未取得・不明・不一致なら要求対象の図は未取得と示す。一致しても図は調査時点の参考情報で、Snapshotの一部ではない。書込・確定手順の改修はBで行う。

## 入力候補・日時と変更手続き（B）

登録・訂正は、対象レコードの設備を明示して扱う。設備名・コードは検索語として自由入力し、既存設備から候補を表示する。登録コード・内容・出典・数値には登録済み入力の参考候補を示す。候補がなくても手入力でき、取得しただけでは値や安全性を確定しない。

| 入力欄 | 候補・操作 | 制約 |
|---|---|---|
| 4カテゴリの検索用設備名・コード | 設備の直接検索。名前・コードを候補表示 | 入力をIDとみなさず、候補外の検索語も保持 |
| 検索コード・新規入力コード | 登録済みの同カテゴリのコード | 新規では重複の可能性を案内。訂正では変更不可 |
| 記録内容・出典・単位等 | 登録値と対象・版・期間・出典を提示 | 同じ値でも異なる出典をまとめない。選択と手入力を両立 |
| 能力・数量・金額 | 同じ設備・製品・期間・単位の参考値 | 空欄を0にせず、取得時に手入力や宣言を上書きしない |
| 費用項目・製品別損害額 | 同じ対応案・費用種別、または製品の登録値 | 異なる製品や費用種別の値を混ぜない |
| 製品・保全予定への参照 | 既存検索結果・次回保全候補から選択 | 存在しないIDを作らない。保全予定の関連付けは解除可能 |
| 種別・安全判断・真偽値・確度 | 既存契約の選択肢 | 自由入力で許可値を拡張せず、安全を自動で充足扱いにしない |
| 日時・期間 | 日本時間の日時選択 | 未編集時の元値と小数秒を保持。編集時だけtimezone付き値へ変換 |

候補は明示取得または欄を選んだときに読み込み、最大20レコード・詳細同時4件・各欄40候補まで。続きや失敗を「なし」にしない。更新実行後の候補は更新前とし、再取得まで入力候補に使わない。取得によって編集中の値を変えない。

変更タブは設備未選択でも要求IDから開ける。保存要求は起点の変更と切り離して保持し、認証切替では破棄する。無効ボタンには次に必要な操作を表示する。保存内容の確認→別担当者の承認→元依頼者の実行を分け、権限・期限・version・Snapshotの最終判定はサーバが行う。値を編集した場合は出典・確度・確認済みの条件を見直す。


## 入力4カテゴリの変更準備完了から承認への引き継ぎ

経済・能力・安全・対応計画／故障履歴の変更準備が成功したら、入力画面に残し、完了・変更要求ID・IDのコピー・サーバが保存した内容の要約を表示する。登録値はまだ変わらず、次は別の工場管理者による承認であることを明示する。準備成功だけでタブを移動しない。

- 成功済みと同じ内容は作成ボタンを無効にし、作成済みという理由を表示する。入力内容を変更した場合だけ別の変更準備を作れる。編集後も既存の要求IDと保存内容を残し、現在の編集が未保存であることを分けて示す。同じ内容の通信失敗後の明示再送は、既存の再送キーを維持する。
- 「保存した変更要求を開く」を明示操作したら、対象IDを欄へ引き継いで保存状態を読み直す。取得失敗でもIDを保持し、再取得できるようにする。承認・実行・書き込みの自動再送は行わない。
- 自然文の指示による作成ボタンは「変更指示から準備を作成」とし、入力フォームからの変更準備と区別する。要求IDが空・形式不正・通信中のため取得できない場合は、ボタン付近で理由を表示する。
- この成功後の導線修正に、通信中断時の処理中解除やタイムアウトの追加は混ぜない。中断時に処理中が残る不具合は別の修正として扱う。

入力4カテゴリの作成ボタンは、通信中だけ「変更準備中…」と待機カーソルを使う。成功済みは「変更準備を作成済み」と通常カーソルで示す。完了パネルは枠と背景、強調した見出しでフォームと区別し、要求ID・保存内容と次の操作を近接させる。

全6タブに適用する統一的ルールの定義・状態別表示・Claude案の原則との対応は、[統合UI改修案§11.2](post265-ui-correction-plan.md#uiデザインに統一的ルールと使用感を適用する)を参照する。共通の無効スタイルは待機中を意味しない。待機カーソルは、実際に処理中であると指定された操作だけに使う。

共通状態の規約は[UI改修計画§11.2](post265-ui-correction-plan.md)に、操作ごとの現状・分類・後続順序・状態の確認手順は[UI操作状態の監査](ui-operation-audit.md)に維持する。コードを共通部品にしたことや静的なOKを、全UIの動作確認の代わりにしない。権限・更新の確定・再送の契約は文書入口が示す業務正本に従う。

## 書き込み結果の確認と失敗表示（W1・直結W2）

入力4カテゴリの変更準備と、保存要求画面の準備・承認・拒否・実行は、`OperationFeedback`の同じ表示を使う。通信状態の管理はその専用hookで行い、APIの実行・入力と再送キーの固定・成功応答の解釈は各操作へ維持する。新APIや書き込みの自動再送は加えない。

- 書込の応答喪失・不正な応答・中断等で成否を確認できない場合は「処理結果を確認できません」と表示する。未作成・未実行とは断定しない。明示的な権限拒否等とは分け、コードと診断用IDは技術情報へ置く。
- 変更要求IDが分かる場合は、そのIDを表示し「この変更要求の保存状態を確認」からGETする。書込の再送ではない。ID不明なら直近の別要求を今回の結果と表示しない。
- 4入力の結果不明後は、送信時と同じ入力・同じ保持済みキーの明示再送だけを許す。入力が変わった場合は理由を示して再送を無効にする。自然文の準備も同じ指示・同じキーを使用する。結果不明の承認・拒否・実行は先に保存状態を確認する。
- 成功応答を受けて要求IDを確認した後、保存状態のGETだけに失敗した場合は、操作の完了と取得失敗を分けて表示する。特に実行応答を消して未実行扱いにせず、同じ要求IDのGETを案内する。
- 存続中の画面で中断が発生した場合は、処理中を解除して結果不明等へ移る。閉じた画面・認証解除後へ遅い応答を反映しない。親の対象／接続用signalが既に中断済みなら、そのEditorから再送しない。
- 入力と再送キーの保持は画面のメモリ内だけであり、接続・対象変更や画面を閉じた後の保持を約束しない。認証情報を保存せず、この変更で永続的な復旧機能や承認一覧を追加しない。

この適用範囲は書込と、その保存要求の取得。検索・比較・質問など全UIの失敗表示まで統一済みとはしない。実書込の通し確認は明示許可前の未検証項目として残す。

### 明示拒否コードの根拠と副作用の境界

`OperationFeedback`の`failed`は、**今回の試行が要求どおりに成立したとは扱わず、明示された拒否理由を表示する**分類である。「DBが不変」「要求が未保存」「過去にも未実行」を意味しない。要求・承認の失効や監査の保存は起こり得る。成功応答と要求IDを確認した後のGET失敗は、コードにかかわらず`confirmed-read-failed`を優先する。

当初の説明表にあった12コードを、今回の対象経路（4入力Prepare、自然文Prepare、承認・拒否・実行、保存要求GET）で静的に照合した。以下は実DBで再検証した結果ではない。

| コード | 確認した発生箇所・意味 | 残り得る記録・注意点 | 表示分類 |
|---|---|---|---|
| AUTHENTICATION_REQUIRED | `http_logging`の認証入口、各serviceのTrusted Context検証 | 当該handlerの更新前に拒否。アクセスログ等まで無いとはしない | 明示拒否 |
| AUTHORIZATION_DENIED | `approval_policy`の職務・自己承認、`execute`のowner・閲覧権限、入力Prepareのrequire | 今回の対象操作を許可しない。失敗監査等が残り得る。既存の要求の不存在を意味しない | 明示拒否 |
| INVALID_ARGUMENT | 入力Prepareの正規化、AgentInput、承認hash・ID形式検証等。Execute途中の例外も主transactionからrollbackする | 失敗監査が残り得る。自然文Prepare後の読取失敗は`AgentService._prepared`がIDを保持した準備結果へ変換する | 明示拒否 |
| INVALID_TOKEN_FORMAT | Frontend `api/client.request`のHeaders作成失敗 | サーバ由来ではなくfetch実行前のclientエラー。この試行では送信していない | 送信前の失敗 |
| VERSION_CONFLICT | `approvals._conflict_code`、各入力Approval、`execute`の対象version検証 | 承認側はINVALIDATEDと監査をcommitしてから409。Execute側は主更新をrollback後、別transactionで失効・監査を保存し得る | 明示拒否。DB無変更とはしない |
| APPROVAL_EXPIRED | `execute_policy.validate_new_execute`と承認消費直前の期限検証 | 主更新rollback後、`execute._retire`がEXPIREDと監査を保存し得る | 明示拒否。期限切れ状態を確認する |
