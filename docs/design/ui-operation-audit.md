# UI操作状態の監査と後続修正計画

## 1. 目的と適用範囲

PR #270のmerge後のコード（main `cf7da28`）を、[統一的ルール§11.2](post265-ui-correction-plan.md#112-情報の塊タブ順要約帯)に照らして読む。変更準備が終わったのか、他者を待っているのか、障害なのかを利用者が区別できることを目的とする。部品を共通化すること自体を完了条件にしない。

本書は静的監査・修正順・ブラウザ確認手順の文書である。実装・実環境の操作・試験の実行は今回行わない。業務権限は[access-control.md](../requirements/access-control.md)、更新の確定と再送は[transaction-design.md](../implementation-design/transaction-design.md)が正本。新しい権限・API・自動再送を定義しない。

## 2. 判定と確認の強さ

| 判定 | 意味 |
|---|---|
| OK（静的） | 対象の状態の表示・操作経路がコードにある。実画面で使いやすいことや、通信・更新成功を証明しない |
| バグ | 定義済みの規約と実装が一致しない。再現の有無を別に記録する |
| 設計上の問題 | 現行規約どおりでも利用者が迷う。文言・配置・操作手順の改善が必要 |
| 規約の穴 | 状態・次の操作・結果の意味が未定義。先に判断を記録する |
| 未確認 | コード読取だけでは確定できない。再現方法・追加確認を記載し、OKに数えない |
| — | その操作に適用しない状態。省略と未確認を区別する |

「統一できた」は、合意した対象範囲の各操作・適用状態が規約を満たし、必要なブラウザ確認も済んだ場合に限る。静的OKだけで全UIを検証済みとはしない。適用外をOKとして水増ししない。

## 5. 優先課題と根拠

### W1：書き込みの結果不明・処理中の解除（最優先）

**S4（結果不明）とS5（失敗）の表示は、4つのEditorとActionPanelで共通の部品へ集約し、画面ごとに個別修正しない。** 結果・原因・既知の要求ID・許される明示操作を渡して同じ意味と使用感にそろえる。書込の実行・再送キー・中断・確定後GETの区別は各処理の責務として維持し、表示の共通化によって権限や再送契約を変更しない。既存PreparedInputFeedbackの完了表示との関係も実装時に整理する。

4つのEditorとActionPanel.runは、`signal.aborted`のときbusy解除を省く。既存の調査記録では中断を注入した場合の処理中残留が確認されているが、実利用で何が中断を起こしたかは未特定。アンマウント後にstate更新をしないこと自体は正常であり、この条件だけを根拠に全中断をバグとしない。存続中の画面で結果不明へ遷移できない問題と、古い応答を無視する正常な処理を分けて修正する。

- 変更準備の応答喪失、承認／拒否／実行の応答喪失、操作成功後の保存状態GET失敗を別々に確認する。
- IDがある場合はその要求を開く。IDがない場合は「直近」の別要求を新しい操作の結果と断定しない。保持した入力・既存の再送キーと正本契約に沿う明示操作だけを案内する。
- 処理中を解除するためだけに、自動再送・タイムアウト・新しい書込要求を追加しない。未送信か送信済みか分からない状態を「未作成」と表示しない。
- 復帰方法に新APIや新しい業務規則が必要なら、影響を報告して止める。安全入力Panelの15秒制限は読取専用で、EditorのPrepareには適用されていない。

根拠：[各EditorとActionPanelの調査履歴](../history/2026-10-20-economic-prepare-handoff.md)、`frontend/src/features/{economics,capacity,safety,maintenance}/*Editor.tsx`、`frontend/src/features/actions/ActionPanel.tsx`、`frontend/src/api/client.ts`。

### W2：制限・失敗・結果不明の表示

各EditorはApiErrorのコードを通常のalertに直接表示し、保存結果不明でも一律に再送説明を出す。各Panelも一部はコードを直接表示する。UI設計§11.2の平易な原因説明・技術情報の分離と一致しない。単なる文言置換で権限や確定結果を変えず、W1で定めた状態に沿って、理由と明示操作を出す。

### W3：入力不足の説明

ブラウザのrequired検証は働くが、作成ボタンは「変更準備だけでは登録値は変わりません」と表示するため、どの欄が足りないかが完了案内の近くにまとまらない。まず操作してrequired欄へ移れる現行を壊さず、利用者の抜取確認を踏まえて案内の追加要否を判断する。全フィールド用の新しい検証基盤は前提にしない。

### R1：比較・質問の操作状態

RegisteredComparison.runは候補の取得と比較に同じbusyを使用し、表示が「正式入力を確認中」で共通。質問はApp.performのbusyを使い、空欄時の案内や過去回答の鮮度などを別に確認する。コード読取から、同じフックへ全面移行する必要があるとは結論しない。

### R2：読取・接続・鮮度

文書検索結果は調査・比較と異なり、出典タブの更新前判定がfalse固定。ただし設備状態が変わっても文書自体が変わるとは限らないため、すべて古いとしてよいかは規約の穴。文書検索の取得時点と設備情報の取得時点を混同しない規則を先に決める。接続のコード露出と読取の失敗案内も対象とする。未設定の待機上限を、遅いというだけで書込へ流用しない。

## 6. ブラウザでの状態確認表（手順のみ・今回は未実行）

共有環境のLLM・ネットワーク停止は禁止。異常系は制御応答を使い、実書込とは別に記録する。認証情報はURL・画面例・ログへ残さない。

| 状態／対象 | 再現方法 | 見るもの |
|---|---|---|
| 未入力／検索・比較・質問・準備 | 接続後に未選択・空欄を確認。空欄設備検索は別に試す | 前提と開始方法、仕様上の制限と障害が区別できる |
| 処理中／各操作 | 制御した遅延応答を返す | 処理名・対象、二重押下不可、完了後に解除する |
| 完了／4種の準備 | 保存要求の応答を再生する | 入力画面維持、要求ID・コピー・保存内容、別担当者への案内。カテゴリ固有の応答かも明記 |
| 他者待ち／保存要求 | 承認待ち／承認済みの保存応答を役割別に再生 | 誰の番か、押せない理由、本人／他人を混同しない |
| 結果不明／Prepare | サーバへ書き込まず、送信後に通信失敗する制御応答 | 未作成と断定しない。IDなしの復帰、入力保持、二重送信を起こさない |
| 結果不明／承認・拒否・実行 | 操作応答喪失と後続GET失敗を別に注入 | 保存ID保持、書込の再送とGETの再試行を混同しない |
| 失敗／検索・図・算定・比較・質問・文書 | 個別の制御エラーを返す | 原因・明示再試行、他領域の結果保持 |
| 無効／承認・実行 | 保存要求の状態・依頼者・現在利用者を切り替えた制御応答 | 自己承認・期限切れ・別人実行の理由。UIで権限を付与しない |
| 更新前／図・損害額・代替・比較 | 制御した実行成功通知後、未再取得→読取再取得を確認 | 取得済みの値が最新扱いにならず、再取得した対象だけ更新される |
| 実通し／専用環境 | 環境・認証主体・操作を提示し許可後に、Prepare→別manager承認→元requester実行→調査再取得 | サーバ保存値と再算定が一致。応答再生では代用しない |

## 7. 対応順と概算PR

| 順 | 工程 | 想定PR | 目安 | 区切り |
|---|---|---|---|---|
| 0 | 本書・規約参照・ロードマップ・ガントの更新 | 文書1本（本工程） | 0.5〜1作業日 | 実装を混ぜずレビュー可能にする |
| 1 | W1と直結するW2：書込の結果不明と安全な確認導線 | 修正1本 | 0.5〜1.5作業日 | 明示再送契約を維持。まず書込なしの制御応答で確認 |
| 別枠 | 現行版の実書込通し確認 | 確認だけならPR不要 | 許可・環境確認後に見積もる | 事前の明示許可が必要。未実施でも未検証項目を消さない |
| 2 | R1：比較・質問の状態表示、必要と判断したW3 | 修正1本を想定 | 0.5〜1作業日 | 操作単位で問題が確認された範囲だけ修正 |
| 3 | R2：読取・接続の失敗表示と鮮度規則 | 上の修正とまとめるか追加1本 | 0.5〜1作業日 | 文書鮮度の規約を決めてから適用 |

**現在の概算は、文書1 PR＋修正2〜3 PR**。これは全機能の新規実装ではなく、監査で残った操作状態の是正。修正2〜3 PRの見積もりは1.5〜3.5作業日で、レビュー・CI・利用者確認・実書込許可待ちは別。小さな文言変更ごとにPRを分けず、書込の安全な復帰と読取の案内を意味の塊でまとめる。実装着手時に対象・必要な検証数を再確認し、不要と分かった工程を件数のために作らない。

案Bの工程ガイド・案Cの引き渡し案内コピー・実行後の再取得リンクは判断待ちで、この見積もりに含めない。シナリオ2・データ拡充・新API・全画面の全面改修も加えない。20件超の同目的の追加検証は、PRを分割して事前確認を回避せず、実装前に理由と件数を報告する。
