# シナリオ1：残項目と改修計画

**状態：PR 1のみ実装承認済み。PR 2はPR 1の報告後に別途承認。** [UI設計案](frontend-redesign-proposal.md)と[画面案](scenario1-wireframes.svg)を合わせてレビューする。本計画の作成・pushは実装承認ではない。

## 1. 完成させる流れ

初期画面には設備を決め打ちで表示しない。利用者が設備名の一部または完全な設備コードで検索し、第1加工機M-204を選ぶ。その後は明示的な読取処理で、影響・上流依存・登録状態・推定損害額・代替候補と能力評価を自動取得する。

- M-204：登録上の状態は停止中。下流の工程・製品P-100／P-200を表示する。上流依存も切替で確認できる。
- 損害額：登録条件に基づく200,000円／時間。内訳はP-100の120,000とP-200の80,000。Frontendで合算しない。
- 代替：M-208を登録された代替候補として図と提案に表示する。候補を利用者が暗記して指定する前提にしない。
- 能力：P-100について必要60・空き80をサーバ値で表示し、見出しは「P-100は、能力面で吸収できる見込み」、直下に「今回選択した能力入力ではP-200を評価していません」とする。P-200を含む全業務の置換・安全・品質・実復旧は保証しない。
- 任意でM-208を調査対象にすると、登録上の状態は稼働中、停止損害は算定対象外と表示する。

## 4. JSONとローダーの設計

提案ファイルは `docs/demo/data/scenario1.json`、CLIは `linescope seed-demo-file --file /data/scenario1.json`。形式の詳細は投入手順を参照する。PR 1で[JSONと投入手順](../demo/scenario1.md)を実装した。

| JSONの区分 | 内容 |
|---|---|
| schema_version | 形式の版。未知版・未知field・重複キーを拒否 |
| equipment | コード・名称・種別・登録状態。第1加工機STOPPED、第2加工機RUNNING。名称へ異常内容を埋めない |
| processes／operations／products／infrastructure | 既存構成をコード参照で記述。P-10／P-20、OP-30／OP-40、P-100／P-200と、M-208側のP-30／OP-50／P-300、電源R-02 |
| assignments／relations | 設備・作業の割当と依存関係、M-208 CAN_SUBSTITUTE M-204。有効期間・必須宣言も明示 |
| economic_inputs | M-204に製品別incident_losses。率120000／80000、独立性・出典・確度を明示。既存正規化が要求する他の項目も省略せず、不明は不明とする |
| capacity_inputs | M-208・P-100。必要60、通常120、使用中40、予約0、互換性・負荷独立・網羅true。数量単位・期間・出典・確度を明示。復旧時刻の推定条件は追加しない |

期間は既存例の2026-10-18T00:00:00Z〜2026-10-19T00:00:00Zへ揃える。これは登録条件の評価期間であり、自動検知した事故発生時刻ではない。表示や日付を更新するためだけに入力期間を黙って変更しない。

処理手順は次のとおり。

1. CLIで指定されたファイルを読む。strict JSON・サイズ上限・既知のschemaとfield・コード重複・参照先存在を検証する。任意テーブル名やSQLをJSONから受け付けない。
2. コードをdemo_idへ変換し、設備tuple・Graph fixtures・正式入力へ整形する。正式入力は既存make_recordのドメイン正規化へ渡す。データ値をPythonへ再転記しない。
3. 一つの外側transactionで既存_lock_seedとseed_graph_rows、正式入力insertを使う。seed_graph_demoのtransactionを外から重ねて原子性を分断しない。既存処理の責務を変えない。
4. 再構築中を拒否し、追加データがある場合は構築済みGraphへの投入を拒否する。既存値・状態・版・履歴を上書きしない。競合・未知参照・後段入力失敗は全体rollback。
5. 同一ファイルの再投入は既存一致を保持し、新規追加・不一致時の扱いを結果で区別する。既存関係の同一性照合は弱めない。

投入は新しい専用Compose project・私有env・独立volumeで行う。migration→JSON投入→Neo4j schema→再構築→Projection→実API照合の順。旧サービス・DB・volumeは削除しない。UI確認環境への切替は検証済みの新環境を対象にし、接続先と保持した旧環境を報告する。

## 5. UI変更計画

[設計案](frontend-redesign-proposal.md)に構成・状態・文言を記載した。

- 左は検索のみ。初期状態では実データの設備カードを出さず、検索後に返却候補を表示する。候補には登録状態を文字と色で示す。状態は下流・上流・代替探索等のサーバ返却値を反映し、未取得候補は確認中とする。全ノード属性の一斉取得には戻さない。
- 一台の調査を中心に、選択後に下流と上流を独立取得する。下流の到達製品があれば代替探索、候補が得られれば能力入力検索と比較へ進む。
- 損害額と提案を図の直下に並べる。登録状態と、入力の自動選択・版・期間・出典を明示する。入力を選び直す操作は可能だが期間は編集できない。
- 初期・取得中・登録なし・稼働中・失敗・対象切替・更新前・狭い画面を設計してから実装する。特定設備コード専用の分岐を作らない。
- 歯車をモチーフにしたファビコンはPR 2のUI改修に合わせて作成・設定する。PR 1では変更しない。
- 既存比較・根拠・入力・承認は下段で保持。状態変更も下段へ移す。自動処理は読取だけ。
