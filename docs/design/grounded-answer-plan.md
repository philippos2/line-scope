# ハルシネーション対応の設計・実装計画

正本との関係：[Agent設計](agent-design.md)の方針を具体化するレビュー用計画。業務範囲・認可はrequirements、HTTP契約はapi-tools、AI評価はevalsを優先する。承認後に対象の正本文書へ契約を確定し、計画書だけを仕様の正本にしない。

状態：開発者の明示した実装指示に従い、同じPR #276にコード・APIの追加回答構造・UI・検証を実装中。DB・データ・モデル設定は変更しない。以下§1〜11は設計時の検討を含み、実装した構成と未対応・確認限界は§12を優先する。設計専用PRは増やしていない。

## 1. 目的・責任・受入

**事実はコードが責任を持ち、LLMには解釈と整理だけをさせる。** コードの責任は認可済みデータの取得、計算、主張と根拠の対応の検証、検証不能な内容の公開抑止を含む。LLMは利用者の意図・対象・欲しい情報の構造化と、検証済み情報の整理を担当する。分類や整理自体も誤り得るため、コードで検証する。

狙いは、登録されていない事実や未評価の運転可否が、確定した事実として出ないこと。全自然言語の意味をコードで完全に証明できると約束しない。検証できる主張の形式を限定し、扱えない質問は範囲・不足を説明する。特定の質問文、設備コード、倉庫・メーカー等のキーワードごとの専用経路は作らない。

受入：

- 未対応の情報を、近くの取得情報で補わない。失敗・未取得・打切りを「未登録」に変換しない。
- 事実欄の各項目が、サーバで生成した取得結果または決定論的計算結果に追跡できる。
- 対象・属性・方向・条件・単位・期間が一致しない主張を事実欄へ出さない。
- 登録上の状態、構造上の候補、利用可能性、能力、安全、運転許可の意味を維持する。
- 複合質問は、対応可能な部分と確認できない部分を両方残す。単一の定型要約で他の論点を消さない。
- #275で残した対象の優先、表記照合、曖昧さ、ページング、中断・再送の規則を退行させない。

## 3. 全体の処理

1. 認証済みの要求・元の質問・画面補足を分離する。本文の明示対象を優先する。
2. 小さい能力一覧を使い、LLMが「対象の表現・必要な情報種別・操作」を構造化する。
3. コードが形式と対応範囲を確認する。曖昧・未知意図は確認へ戻す。分類不能だからと全Toolと自由回答を無制限に再開しない。
4. 対応するRead Toolだけを広告し、既存のDispatcherで認可・引数検証して取得する。
5. 実取得結果を、型付きの事実と取得状態へ正規化する。生のTool結果・Evidenceは保持する。
6. LLMは事実参照の選択・並び・グループを提案する。主張の内容・値を自由文で追加させない。
7. コードが参照と意味の条件を確認し、事実・確認不能の文章を表示モデルから生成する。解釈として公開するものも検証可能な範囲に限定する。
8. 画面は事実、解釈、確認できない事項、参照元を区別する。

新しい万能Agent基盤は作らない。Read Agentに小さい意図契約、観測変換、回答検証・表示の責務を分けて追加し、HTTP handlerへ業務判断を入れない。

## 4. 範囲ゲートとTool選択（Q2）

能力一覧は質問例ではなく、実装済みの業務データとToolの責務から作る。

| 情報の種類 | 取得候補 | 公開できる範囲 |
|---|---|---|
| 対象識別・登録属性 | 検索／get_* | 許可した属性と実際の登録値 |
| 設備の登録状態 | get_equipment_state | 登録上の現在状態。故障原因・運転許可ではない |
| 保全の計画・実績 | 既存保全Read／登録入力 | 取得した実施日時・記録・適用範囲。0件は未実施の証明ではない |
| 接続・影響・代替候補 | 既存Graph Tool | 関係の型・方向・到達・判定・完全性・未評価事項 |
| 損害・能力・安全・対応案 | 既存入力Read／比較 | サーバの返した計算・判定、選択された入力と条件のみ |
| 関連文書 | 既存検索 | 正本照合された引用。文書の記述と登録された業務事実を区別 |
| 一覧にない属性・情報 | 対応なし | 「この版で参照できる情報の範囲外」。DBに存在しないとは断定しない |

意図の型は`subjects[]`、`facets[]`、`operation`（取得・比較・説明等の許可enum）、`needs_clarification`を候補とする。具体的な公開名と上限は契約レビューで確定。LLMの出力に任意のTool名・SQL・JSONPathを許可しない。対象IDは検索結果との照合後だけ使用する。

複合質問はfacetごとに取得状態を持つ。同じ属性の複数設備比較は、双方を独立に解決する。過去時点や期間、単位が合わなければ比較不能を表示する。修飾語が不明なら確認し、LLMのconfidenceだけで事実としない。

Tool広告は認可済み能力一覧との積集合。対象検索、必要な分野、必要なら一段の追加取得へ段階化する。許可外Tool呼出しは既存境界で拒否する。12回・120秒を維持し、分類・整理のLLM呼出しにも同じ総deadlineを配分する。追加のLLM往復で遅くなる可能性を実測し、Tool数削減だけで高速化したと言わない。

## 5. 事実と主張の内部契約（Q4）

### 5.1 コードが作る事実

`fact_id`は要求内でサーバが割り当て、別要求・別利用者の参照を受け付けない。業務IDやLLMの作ったEvidence IDを採用しない。

各事実の候補フィールド：`subject`（型付き実ID）、`predicate`（許可した属性・関係・判定）、`value`（型付き値）、`qualifiers`（期間・単位・製品・scope・状態version・Graph世代・complete）、`provenance`（実tool_call_idと許可した結果項目）、`observed_at`。コードのadapterがToolの正式schemaから作り、LLMが値を書き込まない。

単一の汎用「JSON内の文字列探し」は使わない。関係ならsource・relation_type・targetを保持し、SUPPLIESの型と電源種別から「保管場所」を生成する変換は存在しない。新属性・新関係を扱うときは、そのschemaと変換規則を追加する。自然言語質問を追加するたびに分岐を追加しない。

未入力・部分成功・失敗も事実値に変換せず、次の取得状態として扱う。

| 状態 | 言ってよいこと | 言ってはいけないこと |
|---|---|---|
| 対応なし | この版では参照できない情報 | 登録がない／対象が存在しない |
| 曖昧／未検索 | 対象や条件が未確定／まだ取得していない | 先頭候補で確定／0件 |
| 取得失敗／打切り／続きあり | 完了できない／取得済み範囲のみ | 全件なし／最新を確定 |
| 正常完了・0件 | この検索条件・取得時点で登録記録0件 | 保全未実施／設備は運転できない |
| 値がnull／UNKNOWN | その値・判定を確認できない | 0円／安全／利用不可 |
| 正常取得 | 当該値と限定を併記 | 別対象・別期間や実運転全体への一般化 |

0件を主張できるのは、指定したフィルタ範囲の完了が確認できるときだけ。最新・最後の日時も、取得の完全性・並び順の契約で保証できる場合に限定する。全ページ取得が予算内に終わらない場合は範囲内の値として表示する。

### 5.2 LLMが提案できる主張

任意の「文章＋根拠ID」では、関係の読み替えを機械的に防げない。初期実装では、次の**型付きの主張**に絞る。

- `fact_reference`：事実IDの参照。文章・値はコードが事実から生成する。
- `relation_reference`：型付き関係またはサーバが返した経路の参照。辺・方向・対象を足さない。
- `assessment_reference`：サーバの判定と、そのscope・unknowns・前提を一塊として参照する。
- `document_quote`：正本確認済みの引用箇所への参照。「文書には〜とある」と出し、業務DBの事実や運転許可へ昇格させない。
- `unavailable_reference`：コードが確認した取得状態への参照。

検証順は構造→参照の要求内実在→対象・facet一致→型・期間・単位・完全性→公開権限・鮮度。失敗した主張は公開せず、そのfacetに「根拠との対応を確認できません」を表示する。独立した有効facetは残し、全回答を一律に成功へしない。

自由な推論文を「解釈」と名付けて通す案は初期実装では採用しない。解釈欄には、既存のサーバ判定や承認された導出規則を使った説明だけを出す。LLMは質問と情報の対応・整理を提案できるが、新しい業務結論は作らない。任意の推論の公開は別の要件判断とし、このPRの完了条件へ勝手に足さない。

LLMが質問の情報種別を誤分類するリスクは残る。画面に「この質問を何の情報として解釈したか」を表示し、利用者が対象・内容を訂正できるようにする。型付き根拠が正しくても質問に答えているとは限らないため、意図の正しさは別の受入軸として実モデルで評価する。別の属性の事実を取得できただけで、その質問に回答済みとしない。

不正JSONは修復用の無制限再生成をしない。安全な確認不能表示へ戻し、診断情報を技術欄に分離する。完全性を損なうのに黙って事実を切り捨てる要約はしない。

## 6. 実装箇所・公開契約・境界

| 責務 | 変更候補 | 保持するもの |
|---|---|---|
| 意図・能力分類 | agent内の小さい型・能力一覧 | 検索／計算・認可をLLMへ委譲しない |
| 観測→事実の変換 | 既存Read結果schemaごとのadapter | raw data、Evidence、version、時点を改ざんしない |
| 主張検証・文章生成 | agent内の検証・表示部品 | 任意の質問文・機材コード分岐を追加しない |
| モデルadapter | Ollama構造化出力の内部オプション | 現行Tool検証・deadline・既存provider失敗契約 |
| API | `/agent`の回答構造の追加 | routeで計算・SQLをしない。既存入力・Tool契約・認可は維持 |
| Frontend | 質問欄の構造別表示・根拠への導線 | 既存左ペイン・上部タブ・会話・無効理由・中断復帰 |
| Q3 | 共通表記候補規則と左検索の接続 | 完全一致／部分一致、衝突、続き、利用者選択の保持 |

API候補は既存`answer`をコード生成の互換テキストとして残し、`data`にversion付き`answer_sections`を追加する。facts／interpretation／unavailableと根拠参照を持たせ、通常表示に内部UUIDを露出しない。契約の正本api-toolsに型・上限・不正時・partialとの対応を明記してから実装する。既存のdata.tool_results／Evidenceを削除・別の意味へ転用しない。古い保存回答やPrepare応答を構造化済みと偽装しない。

DB migration・seed・業務更新・モデルの変更を前提にしない。質問に足りないデータを作って合格にしない。RAGは現在の正本照合を保ち、任意の文書内容を事実predicateとして登録しない。更新質問は従来の明示意思・Prepare境界を保持し、回答分類から書込権限へつなげない。

Q3は同じ対象解決を使う検索の小さい是正としてこのPRに含める案。共有は純粋な表記候補規則に限り、フロントからbackend内部moduleを直接importしない。新HTTP APIなしで可能かを設計承認時に確認する。scopeが大きくなる場合は黙ってPR数を増やさず、3PR計画への影響を提示する。

## 7. 画面の完成像

質問ごとに、対象・取得時点とともに以下を表示する。主張と限定は分けない。

1. **取得した事実**：名称・コード、値、単位、期間、登録上という限定、根拠を開く操作。
2. **結果の解釈**：既存判定・導出規則の説明と評価範囲。該当しなければ空欄を増やさず省略する。
3. **確認できない事項**：未対応・未登録・失敗・不完全・曖昧を具体的に区別する。
4. 回答付近に「AIが質問を解釈して登録情報を整理しています。確認できない事項と根拠も確認してください」を常設。未対策の旧自由回答が表示される期間は「AIが生成した回答です。登録情報にない内容を含む場合があります」と明示する。注意書きは対策の代用品としない。

コピー・読み上げ用の`answer`も同じ検証済み表示モデルから生成し、見た目だけ新しい構造で自由文を混ぜない。質問送信中・成功・部分完了・失敗の共通規約と旧回答の保持を維持する。

## 8. 確認とテストの計画（追加前に件数を確定）

既存の質問ケースを削除・弱体化しない。新規自動試験は**展開後20件**を初期見積もりとし、実装前に確定する。同目的で20件を超える追加が必要なら、件数・理由・削減可否を示して事前了承を得る。PRやcommitで分割して回避しない。全組合せの直積や文言・レイアウトの網羅はしない。

| 対象 | 追加ケース見積もり | 守る性質 |
|---|---:|---|
| 範囲・構造化契約 | 4 | 未対応と未登録、複合・曖昧、不正構造、権限外 |
| 根拠・意味の検証 | 7 | 架空ID、対象違い、属性違い、関係方向、期間／単位、完全性、未評価判定の飛躍 |
| 取得状態・部分結果 | 4 | 0件の範囲、失敗、続き、独立した正常facet保持 |
| 公開表示・対象・検索 | 3 | 限定の保持、内部ID非表示、表記候補の衝突と途中結果 |
| Tool・deadline・更新境界 | 2 | 未広告Toolと更新の拒否、予算内での安全な停止 |
| 合計 | **20** | 既存試験の移設と強化も別途明記し、ケース数を数え直す |

実モデルの受入datasetは別枠で、まず既存例を含む次の失敗分類ごとに対象・言い回しの異なる2問ずつ、計12問を提案する。コード試験の代用や追加20件確認の抜け道にせず、実施件数・負荷も設計承認で合意する。

- 未対応の情報、取得情報から別の意味への飛躍、対象不存在、対象曖昧、失敗・不完全、複合質問と対象切替。
- 消耗品／倉庫、メーカー、コーヒーメーカー等はこの分類に属する例であり、製品の分岐条件ではない。
- 分類ごとに、必要なToolを取得したか、公開された各主張が型付き根拠と対応するか、答えられない事項を区別したかを判定する。回答文字列の完全一致やLLMによる自己採点だけでPASSにしない。
- 同じモデル・GPU条件、model digest、code／schema／dataset版、回数、入力bytes・tokens・往復数・所要時間・失敗を保存する。一回の成功で一般性能を保証しない。実書込はしない。

追加20自動ケースと12実モデル問は提案であり、まだ追加・実行していない。既存質問ケースの同条件再評価も含めた最終総数を着手前に提示し、20件超の事前レビュー基準への該当を明示する。

## 9. 工数・同一PR内の段階

**中規模の改修候補。実装承認後7〜10作業日、実装・検証対象12〜18ファイル程度の暫定見積もり**。設計文書・ガント・過去の変更履歴はこのファイル数に含めない。人のレビュー・承認待ち、CI待ち、モデル設定変更は別。範囲と意味を検証できる述語の上限を承認時に固定する。

| 段階 | 暫定工数 | 終了条件 |
|---|---:|---|
| H0：実モデルの構造化出力・小さい能力一覧の読取検証 | 1日 | 不正・期限超過を含む挙動と取得分野の網羅性を報告 |
| H1：内部事実契約と公開回答契約 | 1〜1.5日 | 述語・限定・欠落状態・API互換を正本へ確定 |
| H2：範囲ゲート・Tool絞込み・事実と主張の検証 | 2.5〜3.5日 | 自由文fallbackを事実欄へ流さず、複合facetの意味を維持 |
| H3：質問UI・根拠導線・Q3の検索整合 | 1〜1.5日 | 限定と確認不能を表示し、対象照合規則を共通化 |
| H4：既存回帰・実モデル・ブラウザ確認・文書更新 | 1.5〜2.5日 | 既存機能と失敗分類の確認、残る限界を報告 |

## 13. H6：曖昧な解釈の確認（採用方針・実装承認待ち）

開発者は、曖昧な解釈へ確認を挟む方針を同じ#276で採用し、具体設計を先に提示するよう指示した。確認は口語の全てには挟まず、口語全般の理解を約束しない。「曖昧」の定義と「違う」の行き先を明記してから実装承認を求める。本節の範囲は条件付きで実装承認されたが、§13.8の試験件数・負荷への承認待ちで未実装。§12の実装記録や「確認操作を追加しない」という従前の範囲を、以下の範囲で置き換える。受入の正本はacceptance-criteria、Agent境界はagent-design、HTTP追加案はapi-tools、画面はfrontend-console、評価はevalsへ反映する。

### 13.1 目的と限界

利用者の問いに対応する登録情報を返すことが目的。識別、拒否、確認クリックは目的そのものではない。「字義どおりの照会は確認なし、解釈を確定できない照会は範囲を示して確認する」を採用する。口語全般の理解、意味の完全な証明、実機監視・運転許可は約束しない。

埋め込み、新しいモデル、三段目の照合、質問・設備別の分岐、非対応語のdeny-list、業務更新は追加しない。activeのようなDB技術フラグは通常の自然文分類から外す。既存の直接Read、API原データ・技術情報は維持し、activeをregistered_stateへ自動置換しない。

### 13.2 「確認なし」「確認待ち」「照会できない」の境界

LLMの確信度と二段目のMATCHだけでは、確認を省略しない。コードが確認するのは限定した構文・型・取得条件であり、任意文の意味の証明ではない。

| 行先 | コードで確認する条件 | 動作 |
|---|---|---|
| 用語の説明 | 対象を要求しない定義構文に質問全体が一意対応 | カタログの定義をコードで表示。設備の状態を取得しない |
| 直接回答（値等） | 対象が実検索で一意、通常参照カタログで定義した字義的な構文に**質問全体**が対応、要求された全項目の対応が一意、疑問の型・時制・入力条件と返せる型が整合 | 既存Readを実行し、登録値・観測範囲を表示 |
| 解釈確認 | 対象は一意で、提示できる参照範囲はあるが、構文に未説明の語句が残る／要求表現と定義の対応が確定しない／同じ箇所に異なる意味の項目が競合する／疑問の型や時制が確定しない | 質問内容のReadはしない。原文と別枠の参照範囲を示す |
| 対象選択 | 対象が複数 | 既存の対象選択。解釈の確認とは別の段階 |
| 取得未完了 | 識別の検索失敗・続き未取得等 | 一意とせず理由と再試行。未登録・非対応と断定しない |
| 確認不能 | 対応する参照範囲がない／構造化抽出が不正／安全に提示できる候補がない | 別の情報を回答に代用せず、質問編集へ。近いfieldを強制選択しない |

「字義的」は、文字の一部が見つかったことではない。対象の実登録名・コードと保守的な表記候補、参照カタログの属性・関係・登録状態値の定義語、疑問の型、明示時点、助詞・接続・句読点等を組み合わせた限定構文として表す。原文の全てが説明できた場合に限る。LLMが指定したspanの合計だけを「全文を説明した」証拠にせず、コードが原文から照合する。説明できない名詞や修飾を勝手に落とさない。複合質問は全節が対応した場合だけ直接回答し、一部だけを元の問い全体への回答にしない。

例として「第一加工機の登録状態は？」は実対象照合後、確認なしで回答する。「登録状態って何？」のように語尾が口語でも定義語と全体構文が明確なら、口語という理由だけで確認しない。用語の説明を返し、選択設備の状態照会に置き換えない。非字義の比喩は、単語別の経路でなく未説明部分が残る条件として確認する。これらは受入の例であり、その文だけを通す正規表現一覧にしない。

### 13.3 カタログと抽出の責務

能力の定義データはBackendのAgent層が単一に所有し、key、表示名、定義、除外範囲、主語型、回答型、時点・入力条件、字義構文の定義語を持つ。既存のFIELD_MEANINGS等と二重に保守しない。仕様の正本はagent-design／api-tools。実装者が管理し開発者がレビューする。単なる表記追加も回帰で確認し、参照する業務範囲・意味を変える変更はPO判断とする。別DB・管理画面・埋め込み辞書は作らない。

| 情報群 | 主語・条件 | 回答型と守る限定 |
|---|---|---|
| 設備名称・コード・業務種別 | Equipment | 登録属性。保証等の別属性へ置換しない |
| 登録運用状態 | Equipment・評価時点 | 登録状態。DBレコード有効性、実機監視、運転許可ではない |
| 保全実績・計画 | Equipment・検索範囲 | 記録／日時／件数。完全取得前に最新・未実施を断定しない |
| 上下流・代替・共通依存・単一障害点 | 既存Toolが要求する型・引数 | 登録関係・サーバ判定。保管先、原因、実運転可否ではない |
| 経済・能力・安全・対応計画の入力 | 既存の対象・製品・期間等 | 登録候補。候補一覧を金額・充足・運転許可へ変換しない |
| 正式入力比較 | 明示選択された入力と期間 | 既存サーバの比較。完全な既存比較選択の経路は維持 |
| 文書 | 検索対象・検証済み出典 | 文書抜粋。現場の実態を確定しない |

原文からの抽出は文字列だけでなく位置を持ち、範囲内・実在・対応する原文と一致するかをコードで検証する。位置は正規化前の原文で検証し、NFKC等の検索用表記候補と混同しない。省略を無理に原文の名詞句へ変えない。抽出の実在検査は捏造を防ぐだけで、抽出漏れや意味の正しさは保証しない。未説明部分と要求の全体性を別に検査し、型・時制だけの一致を意味の一致へ拡張しない。未知の疑問表現を単語一つでLOCATION等へ確定しない。

### 13.4 確認の表示と「違う」の後

確認待ちでは、対象識別以外の業務結果を先に取得・表示しない。確認の塊を折りたたみの外に置き、次を同時に見せる。

- 元の質問：利用者の原文。
- この画面で調べる範囲：実対象の名称・コード、参照能力のサーバ側表示名と限定。値はまだ表示しない。
- 注意：この範囲の結果で、元の質問全体に答えられるとは限らない。
- 操作：「この範囲を調べる」「違う・質問を直す」。単なる「はい」で意味の正しさを確定しない。

「この範囲を調べる」は**利用者が明示的に選んだ新しいRead**として実行する。結果に「元の質問」「選んだ照会の範囲」「その範囲の結果」を残し、元の質問への正答だと昇格させない。保証についての質問から状態を選んでも、保証の回答になったと表示しない。承認・実行・業務権限とは無関係。

「違う・質問を直す」は質問内容のReadをせず、その確認を終了する。「この解釈での照会は行いませんでした。質問を直して送信できます」と表示し、原文を入力欄に残してフォーカスを戻す。違うと答えただけで「その情報は未登録／非対応」と断定しない。別の近い候補を自動で繰り返し提示しない。

質問の編集、起点・認証の変更、接続解除で保留中の確認を無効化する。同じ起点でタブを往復するだけなら保持する。待機・無効理由・失敗・古い結果の表示は既存の統一規約に従い、遅い応答で旧確認を復元しない。確認中も質問を編集でき、二重送信と自動送信はしない。

### 13.5 サーバ境界と追加契約

現行AgentInputは確認choiceを受け取らない。**既存POST /agentへの任意項目と確認待ち応答の追加が必要な設計案**であり、「API変更なし」とはしない。新しいHTTP経路・永続DB・認可規則は追加しない。詳細案はapi-tools末尾。

既存ConversationStoreの利用者所有・TTL30分・一時メモリという性質を再利用し、対象選択の会話とREAD_SCOPE確認をkindで区別する。サーバが原文と時点のhash、確定した対象参照、提案した参照能力、定義versionを保留情報として持つ。clientにTool名・任意の引数・権限を指定させない。

確認受理はPrepare認識・変更再送より先に専用のRead分岐へ入り、元の質問からPrepareを起動しない。確認時に認証・owner・TTL・原文一致・カタログversionを検証し、対象を再照合して元の同一対象へ解決できるか確認する。不一致・複数化・失敗は無断で別対象へ進まず、更新された確認／対象選択へ戻す。実Readでも現在の権限・Graph同期等を再検証する。確認はデータのSnapshotでも、当時の状態を固定する予約でもない。

- 調整用：既存のペアワイズ6問。近傍の最小対は状態／契約有効性、構造代替／部品保管等の意味の境界として残す。

### 13.9 字義構文の照合擬似コード

「登録状態って何？」は用語の定義を尋ねており、選択設備の現在値照会ではない。定義・値・関係・記録の照会を分離する。対象省略を理由に、この定義質問へ画面の設備を自動補完しない。

CatalogEntry = (key, definition, literal_terms, subject_type,
                answer_type, time_rules, required_inputs, grammar_shapes)
QUESTION := DEFINITION | VALUE | RELATION | RECORD
DEFINITION := CAPABILITY_TERM + DEFINITION_END + PUNCTUATION?
VALUE := ENTITY_REFERENCE + PARTICLE? + TIME? + CAPABILITY_TERM
         + VALUE_END + PUNCTUATION?
       | ENTITY_REFERENCE + PARTICLE? + TIME? + REGISTERED_VALUE
         + BOOLEAN_END + PUNCTUATION?

# *_END/助詞は文法、CAPABILITY_TERM/REGISTERED_VALUEは能力定義・登録値の語彙。
# ENTITY_REFERENCEは未解決の原文範囲であり、実検索なしに実在とはしない。

handle_read(question, selection, authenticated_context):
    original = preserve_exact_text(question)
    catalog = business_read_catalog()      # active等の技術フラグを含めない
    parses = parse_all_entire_input(original, grammar=QUESTION, catalog=catalog)
    # 単語包含の判定ではない。未知の名詞・修飾・節を削除しない。
    # NFKC等は対象の候補検索に使うが、原文の位置・意味を置換しない。

    parses = [p for p in parses
              if valid_source_ranges(p, original)
              and no_unexplained_non_grammar_text(p)
              and question_type_and_time_match(p, catalog)]
    # 不正な候補は除外する。複数の有効な解釈は一つへ強制しない。

    if one_unambiguous_valid_definition_parse(parses):
        entry = catalog[definition_key(parses)]
        return DEFINITION(entry.definition, source=CATALOG, version=catalog.version)
        # LLMの自由文・DB取得値ではない。画面選択の状態Readも行わない。

    if one_unambiguous_valid_data_parse(parses):

        targets = existing_real_lookup(refs)       # 名称・コード・表記候補を実照合

        if targets.multiple: return TARGET_SELECTION
        if not targets.found: return TARGET_NOT_FOUND_IN_SEARCH
        if all_subjects_types_inputs_and_facets_match(parses, targets):
            return execute_existing_authorized_read(parses, targets)
            # 実値はcodeが返す。LLMの別field提案で上書きしない。

    # ここから先は推定。原文spanの実在だけでは正しい意味とはしない。
    hint = existing_model_extracts_proposal(original, catalog)
    if invalid_source_ranges(hint, original): return CANNOT_CONFIRM_AND_EDIT
    target = existing_real_lookup(exact_target_reference(hint))
    if target.incomplete_or_failed: return READ_INCOMPLETE
    if target.multiple: return TARGET_SELECTION
    if not target.found: return TARGET_NOT_FOUND_IN_SEARCH
    scopes = admissible_read_proposals(hint, target, catalog)
    # 認証・型・入力の範囲をcodeで検査。近い語を答えへ強制対応しない。
    if scopes.empty: return CANNOT_CONFIRM_AND_EDIT
    return PENDING_CONFIRMATION(original, target, scopes, no_business_read=True)
    # 照会内容をまだ正しい解釈・元の問いへの回答とは扱わない。

accept_confirmation(saved_context, original_hash, authenticated_context):
    verify_owner_ttl_original_catalog_and_same_targets(saved_context)
    return explicit_read_of_displayed_scope_with_current_authorization(saved_context)
    # 元の問い全体への正答としては返さない。Prepare等へ分岐しない。

reject_confirmation(saved_context):
    invalidate_local_pending_state()
    return EDIT_WITH_ORIGINAL_TEXT(no_business_read=True)
